## Context

Six `cas.*` refusal codes (`crates/rezidnt-mcp/src/lib.rs:139-184`: `cas.not_found`, `cas.corrupt`, `cas.too_large`, `cas.not_text`, `cas.not_utf8`, `cas.hash_invalid`) carry doc comments citing this record against the module's standing additive-DEFAULT clause (`:63-73`, confirmed present). DR-057 §Decision 2 ruled `cas_read`'s BEHAVIOR and minted no code name. House practice since DR-035 is one-record-one-mint; this is that mint. `MAX_CAS_READ_BYTES_DEFAULT`'s 256 KiB bound is already correctly DR-057-attributed — untouched here.

**The pivotal finding.** DR-057 §Decision 2 bounds `cas_read` with "v1 serves text mimes only" and treats it as a mitigation. It is not one, as built: `Cas::put`/`get` (`rezidnt-cas/src/lib.rs:45-96`) persist bytes only — no mime is ever written to disk — so `call_cas_read`'s `is_text_mime(&parsed.mime)` gate (`rezidnt-mcp/src/lib.rs:2283`) judges the CALLER's claimed `CasReadArgs.mime`, never the store. A caller who knows a valid CAS address and claims `text/plain` receives it whole, provided the bytes decode as UTF-8, regardless of what was actually written under that hash. `tail_events` is unbadged (doc §12 read class) and serializes whole event envelopes verbatim (`call_tail_events`, `lib.rs:2140-2161`), so every `CasRef` on the log — permit `context_ref` inputs, overflowed `agent.message` transcript blobs, diff refs alike — is discoverable to any unbadged caller before `cas_read` even runs. DR-057 §Decision 4 put `cas_read` in the SAME tier as `board_view`/`tail_events` deliberately, and its own risk register named the generalization risk ("a second consumer... should get its own DR") — this is a RULED consequence, not an implementation defect, but the stated bound does not do what it says, and that gap was likely invisible when the tier was ruled. **Flagged, in the DR-049 Status-field pattern, so the owner can overturn Decision 2 knowingly.**

**A second, narrower residual — log integrity, not confidentiality (I6).** `rezidnt-gate/src/permit.rs:394-408`'s `honest_evidence_ref` strips `cas:blake3:` off `Evidence.cas_ref` and passes the remainder straight to `Cas::path_for` + `fs::metadata` — no shape check, and not routed through `Cas::get` (so no content-hash verification either). That `Evidence` is deserialized from an exec permit verifier's STDOUT (`parse_verifier_output`, `rezidnt-gate/src/lib.rs:139-141`) — a subprocess's output, not caller input, reaches a path join, falsifying DR-057's premise that the MCP tool was the only caller-controlled entry to `path_for`. Not a confidentiality escalation — an exec verifier already runs at daemon privilege and could `stat` anything itself — but a buggy or hostile verifier can plant a `CasRef` on a durable permit-decision fact whose hash addresses nothing real and whose `bytes` is an unrelated file's size; `gate_explain`/`debrief` then resolve an "evidence ref" that is not evidence. The replay property is defeated by data, not tampering.

`Cas::path_for` itself (`rezidnt-cas/src/lib.rs:99-101`) is still `root.join(hash)`; `PathBuf::join` replaces on an absolute component and normalizes no `..`. DR-057's door-level guard (`is_cas_address`, `rezidnt-mcp/src/lib.rs:243-246`) covers only the one caller it added. `rezidnt-gate/src/lib.rs:202-216`'s `resolve_ref` (native-verifier ref resolution) and `permit.rs`'s `honest_evidence_ref` are two MORE callers reaching `path_for`/`get` on unvalidated strings — `resolve_ref` at least re-hashes through `Cas::get`; `honest_evidence_ref` does not.

## Decision

1. **Ratify the six existing `cas.*` codes as named** — `cas.not_found`, `cas.corrupt`, `cas.too_large`, `cas.not_text`, `cas.not_utf8`, `cas.hash_invalid`. No rename, no new code. Strike each "ratification owed (DR-058)" clause on acceptance, pointing here.

2. **THE RULING: `cas_read` moves behind the same badge door every mutating tool already uses** (`check_badge`, dual-path: admitted operator token OR verified agent macaroon) — refused `badge.required`/`badge.invalid` before the mime check, before any filesystem call. `diff_view`/`board_view`/`tail_events`/`get_escalations` are UNCHANGED, still unbadged: they return structural facts, never raw blob bytes. `cas_read` is the one tool in this family that hands back CONTENT, and content is exactly what a badge already gates everywhere else on this surface (doc §12). Verified cost: `rezidnt-operator` (the confirmed intended consumer, DR-038) already performs badged writes (`kill_run`, `resolve_permit`) and threads a badge it already holds — effectively zero added cost. This is a genuine departure from DR-057 §Decision 4 — no prior read tool on this surface carries a badge — but the precedent it matches is doc §12's own content-vs-structure line, not the read/write line DR-057 drew.

   Rejected, recorded: **(a) leave unbadged, state the readable set plainly** — naming a risk does not shrink it, and the fix is cheap. **(c) narrow to diff-reachable refs** — a real, complementary hardening (bounds WHAT is servable, independent of WHO asks) but costlier to build correctly (the fold retains only each worktree's LATEST `last_diff`, so a sound reachability check needs a log scan for every historical `diff.*` ref, not a lookup) and it answers a DIFFERENT threat — an authenticated-but-wrong-scope caller — than the one named, which is an UNAUTHENTICATED local client, exactly what DR-038 §Decision 4's "no local-disk backchannel" language defends against. **(d) persist mime in the CAS** — solves a narrower problem than the one found: an honestly mime-tagged store would still serve `text/x-diff` context-ref bodies and transcript overflow blobs to anyone holding the hash, because those ARE legitimately text. The vacuous gate is a symptom; the unauthenticated read is the disease.

3. **The `honest_evidence_ref` residual (I6) is CLOSED by Decision 4's guard, not deferred.** Once `Cas::path_for` refuses a non-address string, `honest_evidence_ref`'s `path_for(hash)` can only resolve inside the CAS root to a name that IS a content address — the worst case degrades to "stat a real CAS blob that happens not to be the intended evidence," never a traversal or an arbitrary host path. Considered and REJECTED: routing `honest_evidence_ref` through `Cas::get` instead of `fs::metadata` — it would pull the whole blob through the process to read a length `stat` gives for free, an I2-flavored regression for no added honesty once the shape guard lands.

4. **`Cas::path_for` gains a crate-level address-shape guard** — the same 64-lowercase-hex rule DR-057's `is_cas_address` already enforces at the MCP door — returning a new `CasError::InvalidAddress` rather than joining an unvalidated string. Accepted cost: `Cas::get`'s error surface widens for EVERY caller; `resolve_ref` and `honest_evidence_ref` must both map the new variant the same honest way they already map `NotFound` (can't-run / no-ref, never a fabricated pass). The MCP door's own `is_cas_address` pre-check is KEPT, not retired — now defense-in-depth, not the only line; removing an already-tested check for a check that duplicates it would be pure regression.

5. **Three cleanups, folded in.** (i) `codes::CAS_HASH_INVALID`'s message hardcodes the literal `64` instead of interpolating `CAS_ADDRESS_HEX_LEN` — fix the drift risk; no behavior change. (ii) `codes::WORKTREE_UNKNOWN`'s doc (`:91-102`) describes only `release_worktree`; `diff_view` (DR-057) emits it too — widen the doc, not the code. (iii) `rezidnt-types/src/mcp.rs:366`'s `CasReadArgs.hash` doc comment names the PRIVATE `rezidnt_mcp::is_cas_address` inside a field comment now served verbatim over `tools/list` to every MCP client — reword to state the RULE (64 lowercase hex) without naming a symbol no external reader can resolve.
