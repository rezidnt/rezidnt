## Context

DR-042 ratified the orchestrator's shape and closed the live-wiring gate by name (§Decision 5; §Consequences deferral (b)). The owner opened Phase 3 for this arc on 2026-07-24, so this record does not re-argue *whether*; it settles *what*. Intel memo `intel/002-omnigent-capability-comparison.md` F2 is influence/positioning only (DR-002 rule 3) — capability + gap, no code read, nothing ported (I8).

**What already ships.** The read side is built and green: `orchestration_graph` as a pure projection (`crates/rezidnt-state/src/lib.rs:1619`), `LeadRow`/`SubRow`/`VerdictRollup` (`:1584`, `:1529`, `:1567`), the `badge_id` fold (`:431`), the `delegations` fold (`:452`, reducer arm `:1054`), the unbadged read tool (`crates/rezidnt-mcp/src/lib.rs:1718`, dispatch `:543`), plus the two owed guards (`crates/rezidnt-types/tests/orchestration_schema_no_drift.rs`, `crates/rezidnt-state/tests/orchestration_rebuild_equivalence.rs`). What does **not** ship is any writer that produces a real lead→sub edge.

**The defect that sizes this slice.** `bins/rezidentd/src/runs.rs:985-1005` emits `permit.delegated` with `run` = *the run being spawned*, `parent_badge_id` = that same run's base badge (`:998`), `child_badge_id` = its role-attenuated badge (`:999`) — and `agent.spawned.badge_id` is that same attenuated badge (`:929`). The reducer keys the fact on payload `run` (`crates/rezidnt-state/src/lib.rs:1055`), so a role-declaring run's own `delegations[].child_badge_id` equals its own `badge_id`. `orchestration_graph` has **no `sub_run != lead_run` guard** (`:1634-1640`), so today every role-declaring run projects as a lead of itself with `fan_out: 1`. This is untested: `crates/rezidnt-state/tests/orchestration_graph_projection.rs:86-88` builds three *distinct* runs from a hand-authored fixture (`spec/fixtures/dr042_orchestration_fanout.jsonl`) whose lead-keyed, cross-run-child edge **no shipped emitter produces**. The read side is green against a shape production has never emitted.

**Strongest counterargument (recorded, not just resolved).** This is scope gravity, and the sequencing law names it. Phase 3's own headline is the **owned terminal substrate** — the actual herdr-removal endgame (I7/I8; §16 "Phase 3 exit = golden path runs with `substrate = "native"` and herdr uninstalled"). Opening Phase 3 with the orchestrator instead is a real ordering choice with a real cost: it spends the phase's first slice on a capability whose pull is competitive (memo F2) rather than on the dependency that ends an AGPL runtime dependence. The honest answer is not that the objection is wrong — it is that this slice is *composition of shipped rails* (fabric, gates, `AgentSubstrate`, worktree registry, the DR-041 pack, and now a green read side), while the terminal substrate is genuinely new substrate; and the self-edge defect above means the already-shipped read side is currently a **mirage** until a writer exists. Leaving a projection that lies is the worse of the two debts. Two further risks are recorded, not dismissed: **I3 rot** (DR-042 named an orchestrator as the archetypal place log-is-truth decays into a held session object — the temptation is a live `Vec<SubHandle>` in the daemon), and **fan-out load** (N concurrent worktree allocations and N spawns against a sole-allocator registry).

## Invariant posture

- **I1 zero pixels — PRESERVED.** `fan_out` is a headless daemon capability; no render, no board change.
- **I2 control/data never mix — LOAD-BEARING.** The `fan_out` response carries run ULIDs and refusal codes only. Sub work folds back through the *existing* per-run paths (`diff.ready`/`diff.merged` CAS refs, gate evidence refs, DR-043's CAS-pinned content ref, `agent.completed.cost`); no sub diff, dossier, or transcript ever rides the tool response or a fan-out fact.
- **I3 log is truth — THE MECHANISM.** No orchestration session object. The lead holds nothing; it *reads* `orchestration_graph`, a pure fold. Fan-out width stays derived (`:1669`), never stored.
- **I4 substrates behind traits — REUSE.** Subs spawn through the existing `AgentSubstrate` path; isolation is the existing §7 registry. No new substrate, no new backend.
- **I5 MCP-first — HONORED.** The lead is an MCP operator of its subs: one governed, badged, schemars-pinned tool before any keybinding.
- **I6 verifiers — UNTOUCHED, and extended honestly.** Sub verdicts fold through the unchanged DR-041 path; `inconclusive` is never coerced (`roll_up_verdicts`, `:1691`). A sub that could not be *allocated* is reported as refused, never as a passed or failed sub.
- **I7 one binary, no telemetry — UNTOUCHED.** No new crate, no new dep.
- **I8 clean-room — APPLIES.** Memo-traced capability only; nothing ported.

## Decision

1. **One tool, N tasks.** Mint a single mutating MCP tool `fan_out` taking `FanOutArgs { badge, workspace, tasks: Vec<FanOutTask> }`, `FanOutTask { agent, idempotency_key }` — schemars-generated, §9 no-drift, golden-pinned. N separate `delegate` calls are REJECTED: a per-call shape cannot enforce a width cap atomically and cannot report a fan-out as one unit. **Idempotency composes per task, not per call**: each task carries a required key and resolves through the *existing* per-workspace `spawn_keys` map, which is log-derived from `agent.spawned.idempotency_key` (`bins/rezidentd/src/runs.rs:149`, `:229`, `:287`) — no new dedup mechanism. **Partial failure is normal and honest**: the response is a per-task outcome vector (`{run}` or `{code, message}`); a retry with the same keys re-returns the same runs and spawns nothing new. There is no all-or-nothing rollback — spawns are not transactional and pretending otherwise would be a lie. **Authorization**: the lead's own badge passes the existing §12 door with the existing verb `"spawn"` (`crates/rezidnt-mcp/src/lib.rs:563`, `:680`) — a lead macaroon narrowed by a `Verb{spawn}` caveat already authorizes fan-out. No new verb, no new badge kind.
> **Decision 2b AMENDED by [DR-046](DR-046-fanout-limits-edge-and-registry-deferral.md)** — the lead-parented `permit.delegated` emit is **WITHDRAWN as mis-modelled**: a fan-out is not an attenuation, and that subject's ratified semantics cannot carry this event without asserting a narrowing that did not occur. The structural-identity requirement below (`child_badge_id` must equal the sub's folded `agent.spawned.badge_id`) carries over to the replacement fact. Decision 2(a)'s projection guard is unaffected and shipped.
>
> **Decision 6 AMENDED by [DR-046](DR-046-fanout-limits-edge-and-registry-deferral.md)** — its "NOT owed: any orchestration subject" verdict is **OVERTURNED by evidence**. One warden `/subject` IS owed for the lead→sub edge, per DR-042 §Decision 6's own reservation (mint only when the graph genuinely cannot fold from what exists — now demonstrated rather than assumed).

2. **Fix the self-edge at both ends, and stop the projection over-reading.** The DR-017 role-attenuation edge is a **legitimate different fact on a different axis** — a capability-chain record (same run, parent→child caveat hop) that DR-017 minted for replayable authority, not for orchestration. The orchestration projection is over-reading it. Therefore: (a) `orchestration_graph` gains a **`sub_run != lead_run` guard** — a same-run delegation is a capability-chain fact and yields no lead row; (b) the `fan_out` path emits a genuinely **lead-parented** `permit.delegated` keyed `run` = the LEAD's run, `parent_badge_id` = the lead's badge, `child_badge_id` = the badge the sub actually runs under — which MUST equal the sub's folded `agent.spawned.badge_id`, or the graph silently shows `fan_out: 0`. **No discriminator field is minted on `permit.delegated`**: with the guard, "lead-keyed edge whose child badge belongs to a different run" *is* the discriminator, derivable from existing fields. If the build finds a case where a lead must legitimately delegate to itself, that is a warden question — flagged, not invented.
> **Decision 3 AMENDED by [DR-046](DR-046-fanout-limits-edge-and-registry-deferral.md)** (implementation posture only) — the conflict semantics, the refused-sub rule, and the no-retry-loop rule below **stand verbatim**, but the "rides the existing §7 registry" premise is **untrue of the shipped code**: the daemon allocates via its own minimal git-CLI path and never reaches the `GitAdapter` registry. The wiring is deferred to a named slice converging both allocation paths. Isolation today holds by ULID uniqueness of the worktree path, not by any registry guard. The allocator mint referred to below has since landed (`spec/ontology.md:215`).

3. **Sub isolation rides the existing §7 registry, with the lead as allocator — pending a warden mint.** Each sub gets one registered worktree. The allocator value should be the **lead's run ULID** (the "delegating allocator" the two-allocator design anticipates, and the value `spec/fixtures/dr042_orchestration_fanout.jsonl:2` already assumes). That value is **NOT in the ratified v1 vocabulary** (`spec/ontology.md:215`: `allocator: "rezidnt"`, `"human"` reserved; production hardcodes `"rezidnt"` at `bins/rezidentd/src/runs.rs:727` and `crates/rezidnt-adapters/git/src/lib.rs:809`/`:823`), so it may not land before the warden pass in Decision 6. **Conflict semantics**: a double-claim emits at most one `worktree.conflict` and the allocation **returns an error** (`crates/rezidnt-adapters/git/src/lib.rs:777-796`) — it never takes over. A conflicted task is therefore a **refused sub**: no run is minted, nothing folds as `fail` (there is no run to fail), the task's outcome carries the conflict code, and the remaining subs stand. **No in-daemon retry loop** against a sole-allocator registry — that is a livelock, and re-issuing the call with the same keys is the honest retry.
4. **Width cap: DEFAULT 8 subs per call, refused at the tool boundary before any effect.** Configured as `[orchestrator] max_fan_out` in the project spec (a DEFAULT, revisable without a DR). Exceeding it refuses the **whole call** with `FAN_OUT_TOO_WIDE` after the badge door and before any allocation or spawn — zero partial effect, the house pattern. **Honesty:** the plan's §4 supervisor with backoff/circuit-breaker (`rezidnt-supervise`) **does not exist** — there is no such crate and no breaker in the tree — so this cap is the *only* backpressure this slice has. It is not defence-in-depth; it is the single door.
5. **Fold-back is control-plane-clean by reuse, not by new mechanism (I2).** Subs fold back exactly as any run does — CAS refs on `diff.ready`/`diff.merged`, gate evidence refs, `agent.completed` cost — and the lead learns outcomes by *reading* the unbadged `orchestration_graph` tool, which already carries `status`, verbatim `verdicts`, `integrity_alarms`, `cost_usd`, `killed_by`. The `fan_out` response and any fan-out fact carry **no sub content**; that prohibition is a criterion, not a guideline.
6. **Subject verdict: one `/subject` IS owed, and it is not the one DR-042 expected.** NOT owed: any orchestration subject, any lead↔sub lifecycle fact, any discriminator on `permit.delegated` — the graph folds from existing facts once Decision 2 lands. OWED to a warden `/subject` session, **named here and NOT designed here**: widening the `worktree.allocated.allocator` v1 value vocabulary to admit a delegating (lead-run-scoped) allocator. The slice is blocked on that mint for Decision 3's allocator value only; everything else may proceed.

## Consequences

- **Roadmap (§19/§16).** The orchestrator register line moves from ratified-but-gated to **opening**; Phase 2's exit criterion is recorded as met (`bench/harness/tests/real_driver.rs`). The owned terminal substrate remains the other, larger Phase-3 arc and is **not** superseded — this record takes its slot first and says so.
- **Risk register.** ADDS: (1) *I3 rot* — the orchestrator is where a held session object is most tempting; Decision 5 (the lead reads a projection, holds nothing) is the guard, and the fold-equivalence test below is the proof. (2) *Fan-out load* — N concurrent allocations against a sole-allocator registry, with **no shipped supervisor breaker**; the Decision 4 cap is the sole mitigation and is deliberately conservative. (3) *Read-side mirage, now recorded* — until Decision 2 lands, `orchestration_graph` reports every role-declaring run as a self-lead.
- **Test/criterion honesty, plain words.** This record **weakens no test and lowers no bar**; it relaxes no verifier semantics, and an inconclusive sub still folds back inconclusive. It does, however, state plainly that an existing green test is **weaker than it looks**: `orchestration_graph_projection.rs` exercises only distinct lead/sub runs from a synthetic fixture, so the production self-edge case is simply untested and was never caught. The slice owes five machine-checked guards: (a) the §9 write-side no-drift golden pin for `FanOutArgs`/`FanOutTask`; (b) an I3 fold-equivalence test over a **real fanned-out log** (not the hand-authored fixture) — `orchestration_graph(fold(log)) == orchestration_graph(fold(replay(log)))`; (c) a **self-edge regression test** proving a role-declaring run with no fan-out produces zero lead rows; (d) a **width-cap refusal test** proving an over-wide call emits no `worktree.allocated` and no `agent.spawned`; (e) an **I6 test** that a worktree-conflicted task is reported refused and is never counted as a passed, failed, or inconclusive sub, and that a genuinely inconclusive sub folds back uncoerced.
- **Deferred, named.** (a) **Mixed-harness heterogeneity stays OUT** (DR-042 §Consequences (d)) — single-substrate fan-out only. (b) Nested fan-out (a sub that is itself a lead) is out of this slice; the Decision 2 guard is depth-agnostic but untested beyond depth 1. (c) Lead-side cancellation of an in-flight fan-out — `kill_run` stays operator-only (DR-032); a lead may not kill its subs. (d) Cross-workspace fan-out — one workspace per call.

Amendments to this record require DR-045.
