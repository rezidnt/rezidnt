# Intel memo 002 — Omnigent capability comparison across rezidnt's six fronts
**Date:** 2026-07-24 · **Analyst session** · **DR-002 scoped read**

Scope: a roadmap-facing capability comparison of Databricks' **Omnigent** (open-source meta-harness, Apache-2.0,
`omnigent-ai/omnigent`, announced 2026-06-13) against rezidnt across the six fronts rezidnt actually builds on.
This is **capability-extraction for positioning / benchmark / risk-register only** (DR-002 rule 2) — not trait,
ontology, or design input. Design-first is satisfied: every rezidnt front cited below is committed in
`docs/rezidnt-architecture.md` and the DR set. Memo 001 (permission-governance) already covered the permit/policy
axis in depth; this memo deliberately covers the *other* five fronts and treats gates only as the verifier/verdict
contract, not the permit engine. **No competitor code was read** — only Apache-2.0 docs, Databricks blogs, marketing,
and one source-reconstruction aggregator (DeepWiki), the latter flagged and down-weighted wherever it appears.

Target identity is unchanged from memo 001: "Omnigent" = Databricks' meta-harness that sits *above* coding harnesses
(Claude Code, Codex, Cursor, Pi, OpenCode, Hermes, Antigravity, plus SDK agents) and drives them through a uniform API.

## Questions this read must answer
1. **Event fabric** — does Omnigent have an append-only event log / CQRS "log-is-truth" model, or is fleet state held imperatively/in-memory?
2. **Run substrate** — how does Omnigent spawn and supervise agent runs (runner, sandbox, sub-agents, git worktrees, restart/backoff/health)?
3. **Gate/verifier contract** — does Omnigent have a deterministic, interrogable *verifier/verdict* layer (pass/fail/inconclusive, replayable evidence) distinct from its policy/permit engine?
4. **MCP surface** — is Omnigent an MCP *client* (consumes tools), an MCP *server* (exposes orchestration to agents), or both? Transports?
5. **Operator UX** — how does a human observe and steer the fleet (board/fleet view, write actions, escalations, sharing, multi-device)?
6. **Packaging/install** — single static binary vs. hosted service; runtime deps; telemetry stance.

## Findings

### F1 — Event fabric / log model
- **Omnigent has no append-only event log or event-sourced "log-is-truth" model in any primary source read** (confidence: moderate–high, 2026-07-07 / 2026-07-24). The server "remembers the state for each policy and session and passes it to the policy handler" the next time it's called — session state (cost, running risk score, files read/created, original user intent) is **accumulated and held by the server**, presented as behavioral guardrail state, not as a durable event stream. No primary source describes an append-only log, event journal, decision journal, or forensic replay of a past session. Sources: Contextual-Policies blog (https://www.databricks.com/blog/contextual-policies-omnigent-using-session-state-better-govern-ai-agents); Introducing-Omnigent blog (https://www.databricks.com/blog/introducing-omnigent-meta-harness-combine-control-and-share-your-agents).
- **Persistence is a conventional relational datastore, not a log** (confidence: high, 2026-07-24): the server runs Postgres (production/multi-instance default) or SQLite (single-instance lite tier). This is state-of-record storage, i.e. the derived/current view is the record — the inverse of I3. Source: deploy README (https://github.com/omnigent-ai/omnigent/blob/main/deploy/README.md).
- *rezidnt:* the append-only typed event fabric IS the product's spine — every fact append-only, hash-chained, replayable; materialized state is a pure CQRS-lite fold that can be dropped and rebuilt (`rezidnt rebuild`); the log is the compliance artifact and the eval corpus (arch §5, §6; I3). **This is rezidnt's largest structural divergence from Omnigent.**

### F2 — Run substrate (spawn / supervise)
- **Omnigent spawns agents through a "runner" that wraps any harness in a sandboxed session behind a uniform API; a server layer sits above the runner for policy + sharing** (confidence: high, 2026-06-13). Agents are declared in short YAML; swapping harness/model is a one-line change. Sources: Introducing-Omnigent blog; repo README (https://github.com/omnigent-ai/omnigent).
- **Sub-agent orchestration + parallel git worktrees are a shipping, marquee capability** (confidence: high, 2026-06): a lead/orchestrator agent (the "Polly" example) plans and delegates to coding sub-agents running in **parallel isolated git worktrees** so they don't collide; sub-agents can mix harnesses within one orchestration, and one agent can review another's work. Sources: Introducing-Omnigent blog; MarkTechPost (https://www.marktechpost.com/2026/06/13/databricks-open-sources-omnigent-a-meta-harness-that-composes-governs-and-shares-ai-agents-across-claude-code-codex-and-pi/); ChatForest builders-log (https://chatforest.com/builders-log/omnigent-meta-harness-claude-code-codex-cursor-compose-govern-coding-agents-builder-guide/).
- **Sandbox/isolation is real and cross-platform-tiered**: OS sandbox (bubblewrap/seatbelt), network-request interception, and hosted hermetic runners (Modal, Daytona). (High confidence; detailed in memo 001 C3.) Windows isolation is degraded (memo 001).
- **Restart-with-backoff / crash-loop / health-state supervision is NOT described in any primary source** (confidence: moderate on the absence, 2026-07-24). The primary docs cover spawning and multi-interface sync but not an init-style supervisor with backoff, circuit-breaking, or a `Starting→Healthy→Degraded→Faulted` health model. Source: Introducing-Omnigent blog (silent on restart/health).
- *rezidnt:* native `AgentSubstrate` spawn behind a trait (I4); supervisor with exponential backoff+jitter, a crash-loop breaker parking adapters in `Faulted`, and health states published as `adapter.health.changed` facts (arch §7). rezidnt's **worktree registry** (canonicalized path + `allocator` field, `worktree.conflict` on double-claim, arch §7) is the direct analogue to Omnigent's parallel-worktree isolation — but rezidnt frames it as a *fact-emitting allocator/observer* rather than an orchestration convenience. Note: rezidnt does **not** ship a lead-agent-delegates-to-sub-agents orchestrator on the golden path; Omnigent leads there.

### F3 — Gate engine + verifiers (verdict contract, native vs exec)
- **Omnigent has no deterministic, interrogable *verifier/verdict* layer distinct from its policy engine** (confidence: moderate–high, 2026-07-24). Its enforcement axis is the contextual-policy engine (ALLOW/DENY/ASK, stateful) — memo 001's subject. That is a *pre-hoc permission* mechanism keyed on a Python policy function; it is not a post-hoc "does the evidence support the claim" verifier producing replayable pass/fail/inconclusive verdicts with content-hashed inputs. No primary source describes a determinism guarantee (same hashed inputs → same verdict), a three-valued verdict where *inconclusive is never coerced*, or a "why was this blocked, here is the failing verifier + evidence" interrogation contract. Sources: Contextual-Policies blog; Introducing-Omnigent blog. (Consistent with memo 001 Q7/C11: audit/replay is Omnigent's least-documented area.)
- **Policy = imperative Python function** (from memo 001, high): nondeterministic-capable by construction, and the *managed* Databricks tier disallows custom-code policies. Source: memo 001; Databricks docs (https://docs.databricks.com/aws/en/omnigent/).
- *rezidnt:* the gate engine is the differentiation layer. `pass|fail|inconclusive` verdicts (never a bare boolean, inconclusive never coerced to pass); two verifier kinds (native Rust trait + exec argv/JSON contract, the polyglot seam); determinism pinned by content hash with network-off by default; `gate why` / `gate_explain` return the failing verifier + evidence refs; `debrief` re-executes recorded verdicts from log+CAS and raises an `integrity.alarm` on divergence (arch §8; I6; DR-006). **This front is a clean rezidnt structural edge** — Omnigent gates *permission before the act*; rezidnt additionally gates *evidence after it*, and the evidence is replayable.

### F4 — MCP surface
- **Omnigent is an MCP *client*, not (yet) an MCP *server*** (confidence: high, 2026-07-24). Agents authored in Omnigent *consume* external MCP tools (one of four tool types: MCP servers, built-in tools, Python functions, sub-agents), over stdio (local `command`) or HTTP/SSE (remote `url`), declared in agent YAML with optional per-tool filtering. An **"Omnigent Server MCP" — exposing Omnigent's own orchestration to agents — is described as ROADMAP, not shipped** (confidence: high on "roadmap wording," 2026-06-13). Sources: Omnigent tools docs (https://omnigent.ai/docs/build/tools); Introducing-Omnigent blog; DeepWiki MCP page (aggregator, corroborating only — https://deepwiki.com/omnigent-ai/omnigent/5.2-mcp-and-external-tools).
- *rezidnt:* MCP-first is an invariant (I5) — every capability is an MCP tool/resource *before* a keybinding, and rezidnt **exposes its own orchestration as an MCP surface today**: tools (`open_project`, `spawn_agent`, `vet`, `debrief`, `gate_explain`, `tail_events`, `alloc_worktree`, plus read-only `board_view` per DR-039 and `get_escalations` per DR-040), resources (workspace-graph nodes, dossiers, event ranges by ULID, gate defs), over stdio + loopback streamable HTTP, with every tool's JSON Schema generated from `rezidnt-types` so the surface can't drift (arch §9; DR-039/040). **rezidnt ships the "agents are first-class operators of the orchestrator" posture that Omnigent has only scheduled.** Both are MCP clients of downstream tools; only rezidnt is (today) an MCP server *of the fleet itself*. Moderate-confidence differentiator because Omnigent's roadmap could close it.

### F5 — Operator UX (observe / steer / escalate)
- **Omnigent's operator story is real-time multi-interface session sharing** (confidence: high, 2026-06): every session is exposed simultaneously over terminal, desktop/web app, macOS native app, mobile, and REST APIs; teammates can be invited to view sessions, comment on files, and send commands, with messages/sub-agents/terminal state/files synced live across all views. Human steering = the contextual-policy ASK path (pause-for-approval; e.g. approve a `git push` after an npm install, or a cost-cap pause every \$100). Sources: Introducing-Omnigent blog; repo README; Contextual-Policies blog.
- **No read-only-vs-write separation of concerns is described**: Omnigent's collaboration surface mixes viewing and command-sending in the same interfaces; there is no documented "read-only board that provably takes no writer dependencies" analogue. (Confidence: moderate on the absence, 2026-07-24.)
- *rezidnt:* deliberate **split** — a read-only fleet board (S5, ratatui, consuming only watch channels; DR-031 makes it read-only *permanently* to preserve the I1 zero-writer-dependency proof) versus a separate badged MCP **write client** for operator actions (resolve an escalated permit, kill a run). Escalations are first-class facts: `get_escalations` read-only MCP resource (DR-040) surfaces outstanding escalations; the operator-client resolve/live-unblock arc (DR-033/034/035) lets a human resolve a held permit and resume a stalled agent, with resolutions folded from the log (TTL'd, I3-clean). **Different philosophy: Omnigent optimizes live human-in-the-loop collaboration and multi-device presence; rezidnt optimizes an auditable, separable observe/steer boundary.** Omnigent has the richer *presence/collaboration* UX today (mobile, live file comments, multi-view sync); rezidnt has the cleaner *architectural* separation and escalation-as-fact model. Genuine edge in **both** directions — see synthesis.

### F6 — Packaging / install / telemetry
- **Omnigent is a Python/FastAPI service with a relational datastore, deployed as a container** (confidence: high, 2026-07-24): slim Python Docker image (Node web build → Python builder → runtime), FastAPI + WebSocket coordinator, Postgres or SQLite, ~512 MB–1 GB working set; the server does not execute agent code internally (runners do). Deployable on Fly.io, Railway, Modal, Daytona, Kubernetes; also offered managed on Databricks. It is a CLI-installed local tool with optional hosted runners — **not a single static binary**. Sources: deploy README; Deployment aggregator page (https://deepwiki.com/omnigent-ai/omnigent/9-deployment, corroborating); Help Net Security (https://www.helpnetsecurity.com/2026/07/06/omnigent-open-source-ai-agent-framework/).
- **Telemetry: no primary source read mentions telemetry, analytics, or phone-home** (confidence: low-to-moderate — this is absence-of-evidence, not a stated no-telemetry stance). Omnigent does not appear to *advertise* a no-telemetry posture the way rezidnt makes I7 a product stance. Source: deploy README (silent); Introducing-Omnigent blog (silent).
- *rezidnt:* one static binary, `curl | sh` or `cargo install`, no runtime deps, **no telemetry as an explicit product stance** (I7); a real Linux/WSL musl installer with a checksum gate ships today (DR-037). rezidnt's datastore is SQLite-as-log (single-file, `PRAGMA integrity_check` in `doctor`), not a server DB. **Clear rezidnt edge on install friction and the local-first/no-telemetry posture; Omnigent's server+Postgres shape is heavier but buys hosted/multi-device collaboration rezidnt does not attempt (a Phase-1 non-goal).**

## Where rezidnt is differentiated vs. exposed (synthesis)

**Differentiated (lead with these):**
- **Log-is-truth over state-of-record (F1).** rezidnt's single append-only, replayable fabric has no Omnigent equivalent; Omnigent accumulates session state imperatively in a server-of-record. This is the same structural wedge memo 001 identified for permits, generalized: *every* fleet fact is replayable evidence, not just current state.
- **Deterministic, interrogable verdicts (F3).** Omnigent gates permission (pre-hoc, imperative, nondeterministic-capable); it has no post-hoc verifier layer that produces replayable pass/fail/inconclusive with "here's the failing verifier + evidence." This is the compliance-reviewer sentence.
- **Fleet-as-MCP-server, today (F4).** rezidnt exposes orchestration as MCP now (I5); Omnigent has it on the roadmap. Perishable but real as of 2026-07-24.
- **Single-binary, no-telemetry, local-first (F6).** Lower install friction and an explicit privacy stance vs. a Python/FastAPI+Postgres service.

**Exposed (do not overclaim; benchmark, don't assert):**
- **Sub-agent orchestration (F2).** Omnigent ships a lead-agent-delegates-to-parallel-worktree-sub-agents pattern (Polly) as a marquee, working feature. rezidnt has the worktree registry rails but no golden-path multi-agent orchestrator. If "fleet of agents" is the pitch, this is a visible Omnigent capability rezidnt does not yet demonstrate end-to-end.
- **Presence / collaboration UX (F5).** Real-time multi-device session sharing, mobile, and live file comments are shipping Omnigent UX. rezidnt's board is read-only and terminal-first, and multi-device sync is an explicit twelve-month non-goal. rezidnt should compete on auditability and separation-of-concerns, not on collaboration richness.
- **Enforcement breadth (F2, carried from memo 001 C3).** Omnigent's OS sandbox + egress proxy + credential brokering remains a broader day-one enforcement chokepoint; rezidnt's C3 sandbox/egress arc is in progress (DR-025..029) but the honest counter from memo 001 still stands.

## Implications for rezidnt (positioning / benchmark / risk-register only — NOT directives)
- **Positioning:** the "one log, both axes" thesis holds and extends beyond permits — lead on *replayable evidence across the whole fleet* + *deterministic interrogable verdicts* + *local-first single-binary*, and do not lead on collaboration richness or sub-agent orchestration.
- **Benchmark:** add three black-box scenarios to the memo-001 suite (DR-002 rule 6 permits runs): (a) reconstruct every fleet fact of a completed run from the log vs. Omnigent's session state — measures F1; (b) replay a recorded verdict and detect an injected nondeterminism — measures F3; (c) drive a fleet through an MCP-only operator (spawn/observe/escalate/resolve) against both — measures F4/F5.
- **Risk-register:** two live signals to confirm — (1) the "Omnigent Server MCP" roadmap item would erode the F4 edge when it ships (watch the omnigent.ai docs); (2) Omnigent's shipped sub-agent orchestration (F2) is a category-narrative competitor if rezidnt's "fleet" pitch outruns its demonstrated multi-agent path.
