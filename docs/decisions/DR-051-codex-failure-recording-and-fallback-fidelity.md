Its terminal line is `turn.failed` carrying `error.message`; it contains **no `turn.completed` line at all**. The oracle pinned the contract in `crates/rezidnt-run/tests/codex_adapter_turn_failed.rs` (five tests); the implementer mapped `turn.failed → agent.completed{status:"error"}` to close it, carrying the harness's reason verbatim up to a 1 KiB bound and elided-with-a-marker beyond it (`ERROR_MESSAGE_CAP`, added at `47155cf` in response to an I2 debrief finding — an unbounded reason would have made the failure fact unpublishable at exactly the sizes it exists to carry) — commit `4ceccb7` on the same lane as slice A (`worktree-agent-ab4e17a54fbbdb421`; `cargo test -p rezidnt-run`: 145 passed, clippy/fmt clean), ~~pending its own `/gauntlet` and merge — not yet on `main`.~~ **RE-DATED on the ratification pass (2026-07-25): `4ceccb7` is now an ancestor of `main`; the fixture, the five-test oracle (`crates/rezidnt-run/tests/codex_adapter_turn_failed.rs`), `ERROR_MESSAGE_CAP` and the `turn.failed` arm are all present in the tree. Accepting a draft freezes its tense claims — "not yet on `main`" would have become a standing false claim the moment this record was ratified.**

**2. What the recording settles, and what it does not.** DR-050 recorded two positions: the implementer read `turn.completed` as the harness positively asserting termination; the auditor, narrowing, held it asserts only *termination* while `status` is a separate *outcome* claim the codex line doesn't carry — and that claude-code's split `type:"result"`/`subtype`+`is_error` proves the two are distinguishable in principle. The failing recording resolves the empirical question: a turn that ends badly emits `turn.failed`, never `turn.completed`. So `turn.completed` does mean what the implementer read it to mean, **for this recorded version**. The auditor's underlying structural observation is not thereby wrong — codex genuinely carries outcome as one undifferentiated event type where claude-code uses two channels, and that asymmetry is real and worth remembering. What closes is narrower: for codex-cli 0.145.x, that thinner channel does not in fact produce a mismapped success. The refutation is scoped to `TESTED_CODEX_VERSIONS = &[(0,145)]` (the `TESTED_CODEX_VERSIONS` const in `crates/rezidnt-run/src/adapter.rs`); it is a property of two transcripts at one version, not a claim about codex's wire contract in general. Widening that list to a future minor without a fresh recording would silently re-open the exact question this closes — DR-050's Decision 1 (the currently-unreachable version gate) is the mechanism that prevents that, once wired to a live call site.

**3. The "clean residual" was not clean.** DR-050's Context called the daemon's exit-status fallback a clean cover for the unmapped-failure gap — the failure-shaped `agent.completed` literal in `drive_run` (`bins/rezidentd/src/runs.rs`), the one guarded on `completed_id.is_none()` after `child.wait()`; it was at `:1702-1723` as of `da17699`. It does fire, and it does terminate the run honestly as `status:"error"` — but at the time of this record's drafting the literal it published hardcoded `cost:{total_usd:0.0, input_tokens:0, output_tokens:0}` with no `error` key at all. The harness's own failure reason — now proven to exist and ride `turn.failed.error.message` — is **discarded, not carried**. This is a real gap, not a residual to wave past.

**4. The bonus finding: absent usage, not zero usage.** `turn.failed` carries **no `usage` object at all** — a failed codex turn reports zero token *accounting*, not zero tokens. The adapter's `Completion::into_fact`/`reported_usage` already omit the token keys entirely when `usage` is absent, rather than zeroing them (`crates/rezidnt-run/src/adapter.rs`, the `Completion::into_fact`/`reported_usage` pair; the doc there is explicit: "Optional keys are omitted, never emitted as null — a null key would be a present claim of an absent value (DR-012 declared-vs-absent)"). The reducer this feeds is `Option<u64>` end-to-end: the `agent.completed` arm in `crates/rezidnt-state/src/lib.rs` calls `.as_u64()` on `payload["cost"]["input_tokens"]`/`["output_tokens"]`, which is `None` on an absent key, never a coerced `0`. Named plainly: without this, DR-048 slice C's collator would have scored a failed codex candidate as a **free run** — a zero-cost win against every candidate that actually spent tokens and lost. Pinned by `turn_failed_reports_usage_as_absence_not_zero`.

**5. Where absence stops surviving: the `debrief` CLI edge.** The `cost` block of the `rezidnt debrief <run>` command in `bins/rezidnt/src/main.rs` — the surface `/debrief`, the done-gate, reports through — built its `cost` object directly from the folded `Option<f64>`/`Option<u64>` fields, as `serde_json::json!({"total_usd": r.total_usd, "input_tokens": r.input_tokens, "output_tokens": r.output_tokens})`. **That literal is exact as of `d91a7ea`, where the defect is LIVE, and is superseded by the commit that lands this record — which replaces it with a `serde_json::Map` built per key under `if let Some(...)`, the fix Decision 5 prescribes.** Stated in that two-ended form deliberately: it is true before that commit and true after, so it needs no re-editing tomorrow. Quoted code is a tense claim exactly like a line number — an earlier revision of this note asserted the fix had already landed at `d91a7ea`, which was false; the fix was sitting uncommitted in a working tree, and reading a dirty tree as `main` is its own species of not-yet-true claim. Serde's default `Option` serialization turns `None` into an explicit JSON `null` — the reducer's honest absence survives the fold and dies exactly at the report a human or the auditor reads, becoming a **present claim of an absent value**, the precise thing `into_fact`'s own doc (citing DR-012) forbids. This is **not codex-dormant**: `AgentRunState` derives `Default`, so `total_usd`/`input_tokens`/`output_tokens` are `None` until an `agent.completed` fact folds — `rezidnt debrief` carried no guard against being called before a run completes, on any harness, as of `d91a7ea` — closed by the commit that lands this record. The auditor surfaced this while reviewing the codex fallback fix; its reach is broader than codex.

## Decision

1. **DR-050 §Context finding 3 is SETTLED BY RECORDING, scoped to codex-cli 0.145.x.** The codex `turn.completed → status:"success"` mapping is confirmed; the auditor's mismapped-failure branch is REFUTED for `TESTED_CODEX_VERSIONS = &[(0,145)]` only — not generalized to any other codex-cli version, past or future. The auditor's structural dissent (one undifferentiated event type vs. claude-code's two channels) stands as accurate description, not as an open risk for this version window. *(Alternative — treat the recording as settling codex's contract in general — REJECTED: one version's transcript proves one version's behavior; DR-050's own Decision 1 names the mechanism, once wired, that must gate any future widening.)*

2. **DR-050 §Consequences risk item 5 is STRUCK.** "A mismapped codex success would score as pass under I6, with no recorded transcript proving the mapping wrong" is refuted by the recording named above, for codex-cli 0.145.x. Risk to any version outside `TESTED_CODEX_VERSIONS` is already covered by DR-050's risk item 1 (no live version gating today) — it is not a new, separate risk.

3. **DR-050's "clean residual" claim is CORRECTED, not struck.** The daemon fallback (`drive_run`'s `completed_id.is_none()` literal in `bins/rezidentd/src/runs.rs`; `:1702-1723` as of `da17699`) fires and terminates honestly, but discards the failure reason. This is folded into DR-050 §Decision 2(c) as amended below — it does not stand alone as a new decision, since (c) already targets this exact literal.

4. **DR-050 §Decision 2(c) is SHARPENED: the cross-crate pin must compare FAILURE payloads, not a key-set over success payloads.** As originally drafted, (c) asked for "a cross-crate test" pinning the daemon's fallback literal against `Completion::into_fact`'s shape. The auditor showed a key-set-equality test over the two SUCCESS payloads would pass today while `drive_run`'s fallback literal (`bins/rezidentd/src/runs.rs`; `:1706` as of `da17699`) keeps emitting `{"input_tokens":0,"output_tokens":0}` for a run whose harness reported no usage at all — same keys, opposite meaning: `0` says "measured, and it was nothing," the fallback's `0` would say that about a run that was never measured. That is a semantic contradiction the original criterion could not catch. Amended text for slice B entry criterion (c): *the second `agent.completed` fallback literal must be pinned against `Completion::into_fact`'s FAILURE-shaped output (a run that terminated with no usage reported) as well as its shape, and must carry whatever error text the dying child's last stream line reported rather than emitting a bare zeroed literal — a passing key-set-only test is not sufficient evidence this criterion is met.*

5. **A new DR-048 slice-C entry criterion is ADDED: absence discipline must survive to every consumer of `AgentRunState`'s cost fields, not just the reducer.** `rezidnt debrief`'s existing cost block (in `bins/rezidnt/src/main.rs`) emitted explicit `null` for an unfolded cost field as of `d91a7ea`, independent of codex — a live, reachable defect at that commit, not a dormant one, fixed by the commit that lands this record. Slice C's collator/leaderboard reads the same `Option<f64>`/`Option<u64>` fields; if it renders them the same way, it inherits the same defect at a higher-stakes surface (a leaderboard, not a debug report). Fix at both sites in the same pass: omit absent keys rather than serializing `None` as `null`, mirroring `Completion::into_fact`'s convention. *(Alternative — treat `main.rs`'s bug as out-of-scope, filed separately from Trials — REJECTED: it is the same absence-discipline question this record is otherwise about, discovered by the same review pass, and DR-048 slice C is about to build a second, larger consumer of the exact fields that leak; fixing it once, here, is cheaper than fixing it twice.)*
