## Context

A `/debrief` on the DR-049 lane found the record's own banner does not match its diff. The verdict, stated plainly: **the defect is an incomplete ledger, not unauthorized work** — every item below was already decided in substance by DR-049 §Decision 2 or 3. What follows records that adjudication, not a re-litigation.

**Five undisclosed mints, each with its own house precedent** (item (e) added 2026-07-25 on the ratification pass — a `/debrief` found the corrected ledger still one short, which is why the count moved from four to five; the correction of an incomplete ledger is itself auditable):

**(a) A new trait method on `McpSubstrate`** (`crates/rezidnt-mcp/src/lib.rs`, MCP core's daemon seam, defaulted — no existing implementor breaks). This is **not an I4 violation**: I4 binds the four §7 traits (`ProcessSubstrate`/`AgentSubstrate`/`RepoSubstrate`/the reserved `TerminalSubstrate`); `McpSubstrate` is not one of them. [DR-011](DR-011-permit-pdp-config-seam.md) §Decision 1 is direct, settled precedent — it added `permit_config_for` to this same trait and recorded "additive to the core seam; no invariant text is rewritten" (amending §9, not §7). That argument is won. What is lost is narrower: the banner is a factual claim about the diff, and "NO trait method" was false regardless of which invariant, if any, the method touches.

**(b) A new mutating MCP tool `release_worktree` plus its `ReleaseWorktreeArgs` schemars type** on the §9 register. [DR-044](DR-044-live-lead-sub-fanout.md) §Amends is the precedent shape: "MINTS one mutating MCP tool `fan_out` plus its `FanOutArgs`/`FanOutTask` schemars types." DR-049 §Decision 3 already required this exact tool ("exposed MCP-first (I5) on the write-capable operator surface") — it was never optional, only undisclosed.

**(c) A new refusal code `worktree.unknown`.** [DR-045](DR-045-fan-out-lead-only.md) §Amends is the precedent shape: "Mints ONE additive refusal code." Additive, dotted-lowercase, tolerated by older peers per the existing convention.

**(d) A breaking response-shape change to the DR-039-governed `board_view` read.** `WorktreeRow` drops `status`, gains `lifecycle` + `outcome` — this is DR-049 §Decision 2 itself, already decided and already disclosed as a fold-shape migration in DR-049's own risk register (item 2). What was missing is the cross-reference: this changes a shape [DR-039](DR-039-board-view-mcp-resource.md) fixed, and nothing in DR-049 says so.

**(e) A new additive-optional payload field `worktree?: string` on the ratified `gate.failed` v1 subject.** `spec/ontology.md:79` (table cell) and `:330` (payload block) both attribute it to this lane; it is emitted at `bins/rezidentd/src/gates.rs` (the `pre_merge` failure path, guarded on `exec_cwd`) and folded at `crates/rezidnt-state/src/lib.rs` under a `DR-049 criterion (c)` comment — lane commit `df61f89`, ontology entry `4bab765`, both ancestors of the merge. The house ledger vocabulary enumerates fields explicitly, not just subjects ([DR-044](DR-044-live-lead-sub-fanout.md)'s §20 row names `FanOutArgs`/`FanOutTask` field-by-field; [DR-045](DR-045-fan-out-lead-only.md)'s names the refusal code by its constant), so "NO subject" was true and nonetheless insufficient — a payload-field mint on a ratified v1 subject is a taxonomy change, warden-routed, and DR-049 §Decision 6's "any further new or changed subject this slice discovers goes through `/subject`; none is expected" reads as a prediction the lane then falsified without amending the banner. It is additive: `v` stays 1, existing fixtures stay valid unchanged, and it carries a DR-012 declared-vs-absent value-semantics ruling (present IFF the gate executed against an allocated worktree; absent on the pre-spawn `vet` refusal; never synthesized to `""`). Already authorized in substance: acceptance criterion (c) — a failed tree folding `outcome = failed` — is unreachable without failure attribution, and the ontology entry records why the correlation-keyed alternative is unsound (one correlation spans every sibling run of a spec).

**1. Risk escalation — the post-restart gap.** DR-049 §Consequences risk (1) accepts failed-tree accumulation as "bounded only by operator discipline." That is optimistic: `Daemon::allocations` is process-lifetime, so after any daemon restart a retained failed tree is no longer reachable by the MCP release door at all. It refuses **loudly**, with `worktree.unknown`, never silently — I6-consistent, and the auditor ruled this is **not a DR-049 criterion gap**: criterion (c) asserts a failed tree survives and a manual release closes it, and says nothing about surviving a restart. But past a restart, accumulation is bounded by **nothing** — the only door that could close the tree can no longer reach it, and today this fact lives in a single rustdoc line (`runs.rs`), not in any record.

**2. The ordering exposure — named, not fixed.** The reducer folds `outcome = failed` for **any** `gate.failed` carrying a worktree, gate-name-agnostic. A future gate with an exec cwd, running **after** a merge, could overwrite `merged` with `failed`. No guard is being added, and the reason matters: `spec/ontology.md:330` declares `gate.failed.worktree?` "present IFF the gate executed against an allocated worktree," naming `pre_merge` only as the case "on the golden path" — not as an exhaustive enum. Restricting the fold to `gate == "pre_merge"` would therefore **narrow the ontology from the reducer**, the wrong direction of authority. Stated precisely so it is not conflated again: a `gate == "pre_merge"` predicate is a **content filter** — order-insensitive, keyed on which gate ran — and is **not** the ordering-guard shape DR-049 §Decision 2 already rejected ("an ordering guard ignoring released-after-merged... makes the fold order-sensitive"). The two were conflated in-flight by the implementer's original justification for this trap; that justification is not reproduced here because the auditor refuted it. The exposure stands, accepted, named.

**3. Two door-policy settlements, pulled out of rustdoc.** A comment at `crates/rezidnt-mcp/src/lib.rs:1112` currently carries two policy calls that belong in a record: (i) DR-049 §Decision 3's phrase "operator or lead" is read as a **dual door** — an admitted operator badge OR a verified agent macaroon — rather than `kill_run`'s operator-only door (DR-032); (ii) the release path reuses the existing verb `"merge"` rather than minting a new one. The auditor found both faithful to DR-049's text and defensible on their own terms, but noted plainly that a policy call is not a doc comment's to make permanently — it is this record's.

## Decision

1. **DR-049 §Amends is corrected.** "Mints NO invariant, NO subject, NO trait method, NO new dep" is struck and replaced: DR-049 minted no invariant and no subject — true, but insufficient on the subject limb, since it **did** mint an additive-optional FIELD on a ratified v1 subject — and it **did** add one `McpSubstrate` method, one mutating tool + arg type, one refusal code, and that `gate.failed.worktree?` field — all now ratified here under the precedents above, and all already authorized in substance by DR-049 §Decision 2/3. *(Alternative — treat the missing disclosure as harmless and leave DR-049 as written — REJECTED: a banner is a claim about a diff, checked by exactly this project's own review discipline; leaving a known-false claim in an ACCEPTED record is the same class of thing DR-047 spent eleven entries condemning.)*

2. **The `WorktreeRow` shape change is recorded as amending DR-039.** DR-039 fixed `BoardView`/`WorktreeRow`'s shape when it hoisted the projection into `rezidnt-state`; DR-049 changed that shape without saying so. This record supplies the missing cross-reference; DR-039's Decision 3 is not otherwise reopened.

3. **DR-049's risk (1) is escalated, not fixed.** Post-restart, a failed tree's accumulation is bounded by nothing — no timer, no door, no reachable release path. This is accepted as a **named** risk, matching DR-049's own posture toward pre-restart accumulation (explicit-only release, no TTL, "a later DR may add it"). *(Alternative — build a persistence layer for `Daemon::allocations` now to close the gap — REJECTED here: it is new scope past a paperwork correction, and the honest failure mode (loud refusal, `worktree.unknown`) is materially better than the silent-wrong pattern this arc keeps finding; fix it later, on its own DR, if the accumulation proves costly in practice.)*

4. **No ordering guard is added.** The gate-name-agnostic fold stands. A future non-golden-path gate that runs post-merge against a worktree can overwrite `outcome`; this is accepted as a live, named exposure rather than pre-emptively guarded against an ontology-narrowing fix. *(Alternative — add the `gate == "pre_merge"` filter now — REJECTED: it is a content restriction that narrows what `spec/ontology.md:330` already ratified as multi-gate-capable, decided here rather than silently reintroduced as "the fix that was obviously needed.")*

5. **Both door-policy readings are ratified as decided, not descriptive.** `release_worktree` admits a dual door (operator badge OR agent macaroon) — this is a deliberate departure from `kill_run`'s operator-only shape (DR-032), justified because release, unlike kill, is a normal part of a lead's own run lifecycle, not solely a human's prerogative. `release_worktree` reuses the verb `"merge"`; no new verb is minted.
