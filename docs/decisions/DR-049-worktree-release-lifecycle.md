## Context

Every premise below was checked against the tree before drafting (DR-047 §Decisions 2 and 8: a brief is a hypothesis until verified). (i) `release_worktree` has **no production caller** — `bins/` references are comments and test mocks only; every allocation therefore leaks a `notify` watcher plus debounce task for the daemon's lifetime, trees stay on disk, registry entries never close (DR-047 risk-register ADD 1). (ii) The fold collapses lifecycle and outcome into **one `status` String** (`crates/rezidnt-state/src/lib.rs:847` sets `"released"`, `:866` sets `"merged"`), so a release fact after a merge fact would clobber `"merged"` — this is exactly why DR-047 §Decision 5 declined to release at merge. (iii) `RunTaskContext` (`bins/rezidentd/src/runs.rs:1615`) carries the worktree as a `PathBuf` only; the daemon cannot call the `WorktreeId`-keyed release verb without threading the id. (iv) The adapter's release verb is **already built and tested**: it drops the watcher (closing the mpsc, which ends the debounce loop), removes the tree, closes and persists the registry entry, and emits `worktree.released` `{path, branch?}`. The slice's work is callers and the fold, not the verb.

**Strongest counterarguments, recorded.** Against Decision 1: a merged tree might hold post-merge forensic value. It loses to I3 — the merged diff is pinned in CAS and the log; a tree whose content the log can rebuild is not a record, and retaining it retains its watcher. Against Decision 3: explicit-only release means failed trees accumulate until someone acts; a TTL would bound it. The TTL loses because a timer is nondeterministic policy — wall-clock reaping is not replayable from the log and belongs, if ever, to a later DR. The accumulation is accepted and named in the risk register.

## Decision

1. **A merged worktree is released at merge.** After `diff.merged`, the run task calls `release_worktree`. The golden path completes DR-007's lifecycle; trees do not accumulate for successful runs. *(Alternative — retain for inspection — lost to I3, above.)*
2. **The fold's collapsed field is split**: the derived worktree entry gains `lifecycle` (`allocated` → `released`) and `outcome` (`merged` | `failed` | `abandoned` | absent), replacing the single `status`. `worktree.released` sets lifecycle only; `diff.merged` sets outcome only; neither can clobber the other, so the trade DR-047 flagged dissolves. The board's worktrees table and its golden fixture move with the shape. *(Alternative — an ordering guard ignoring released-after-merged — lost: it picks a regression to keep instead of removing the collision, and makes the fold order-sensitive.)*
3. **A failed run's tree survives for triage**, retained until an **explicit** release closes it — operator or lead calls the release verb, exposed MCP-first (I5) on the write-capable operator surface, never the read-only board (DR-031). v1 is explicit-only: no TTL, no timer. *(Alternative — auto-reap on TTL — lost as nondeterministic policy; a later DR may add it.)*
4. **Release drops the runtime resources** — the notify watcher and debounce task die with the release, not the daemon. Verified already implemented in the adapter (`drop(_watcher)` closes the mpsc and ends the loop); the slice owes the production call paths, not the mechanism.
5. **`WorktreeId` is threaded through `RunTaskContext`** — mechanical work owed in this slice; the context today carries only the path.
6. **QUEUED, riding with this slice, not done here:** the warden `/subject` from DR-047 §Decision 4 (the `diff.ready` emitter cell and the `source` attribution) — it moves with golden fixtures, which this slice touches anyway. Any further new or changed subject this slice discovers goes through `/subject`; none is expected — `worktree.released` v1 already exists.

**Acceptance criteria (done = `/vet` + `/debrief`, nothing else counts).** (a) A golden-path run ends with `worktree.released` on the log after `diff.merged`; the tree is gone from disk; the registry entry is closed; the watcher and debounce task are demonstrably dropped (asserted structurally host-side; behaviorally — no `diff.ready` from post-release writes — WSL-side). (b) The fold for that worktree shows `lifecycle = released` **and** `outcome = merged`. (c) A failed run's tree demonstrably survives — on disk, registry entry open, `lifecycle = allocated`, `outcome = failed` — and a manual release then closes it with `outcome = failed` preserved. **Exit demo:** one take — golden run merges and its tree vanishes; a failed run's tree persists; one explicit release call closes it; the board shows both states truthfully.

## Consequences

- **Roadmap.** DR-047 §Consequences ADDS risk (1) — the per-allocation watcher/registry leak — retires when this lands. The DR-047 §Decision 4 warden pass stops being deferred. Phase 3's terminal-substrate arc is untouched.
- **Risk register.** ADDS: (1) *failed trees accumulate until explicitly released* — unbounded by design in v1, bounded only by operator discipline. (2) *fold shape migration* — every consumer of `status` (board render, golden fixture, `s2_worktrees`/`s4_gates` assertions) changes shape in one slice; a missed consumer is a silent-wrong of exactly the class this arc produced eleven of. (3) The watcher-drop *behavioral* assertion is WSL-only (`ReadDirectoryChangesW` blindness, per DR-047); host `/vet` sees only the structural leg.
- **Test/criterion honesty, plain words.** Existing fold tests asserting the single `status` string are **rewritten to the split shape** — a criterion form change, disclosed; the replacements assert strictly more (two independent fields where one was). Nothing else is weakened; no verifier bar moves.
- **Deferred, named.** TTL/auto-reap policy for abandoned failed trees; DR-046's carry-overs unchanged.
