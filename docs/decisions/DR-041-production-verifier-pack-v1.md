# Decision Record DR-041 — Production verifier pack (v1): replace the `tests-pass` exec STUB on the golden path with real §8 verifiers

**Date:** 2026-07-24
**Status:** ACCEPTED
**Amends:** §8 (names the v1 production verifier pack — the real verifiers a `pre_merge` gate runs — atop the ALREADY-BUILT S4 engine + §8 exec contract); §16/§18 (the S4 golden-path `pre_merge` gate stops depending on a shell STUB for its test-suite verifier — the recorded one-take demo's merge is gated by a real cargo-test run). Mints NO new invariant, subject, ontology fact, badge, PDP path, reducer arm, or daemon dependency (a `cargo`/`git` toolchain is a host prerequisite, not a linked crate dep — see the honesty note in Decision 3). Adds a §20 index row.

## Context

S4's engine is built and green: the §8 exec contract (`ExecVerifier { name, argv }` over stdin/stdout, scrubbed env, wall-clock timeout, the three inconclusive traps) is proven, the native pack (`diff-scope`, `forbidden-path`, `bare-mode`, `pinned-version`, `allowed-tools`) is real, and `resolve_one` already resolves a `[gates.<name>]` spec entry into a `VerifierKind::Native | Exec`. But the golden path's test-suite verifier is a STUB: `bins/rezidentd/tests/golden_path.rs` gates `pre_merge` on a `tests-pass` shell script that speaks the §8 contract from a fixture (its own header says so: "the test-suite runner is EXEC-STUBBED … a real cargo-test verifier adds minutes of wall clock and zero new contract surface to this board"). The contract is proven; no REAL verifier ships. This record settles what the v1 production pack IS and how the daemon locates it — it operationalizes §8, it does not extend the contract.

**Strongest counterargument (recorded, not just the outcome):** "The exec contract is already proven by the stub — a real cargo-test verifier adds minutes of wall clock and zero new contract surface. Leave the stub on the golden-path board and ship product depth instead." Its real force is honored: the golden-path *test board* keeps its fast exec stub (Decision 5 does not touch `golden_path.rs`'s stub — a real cargo-test there would make the one-take demo slow and toolchain-fragile for zero contract gain). But the counterargument fails as a reason to ship NOTHING real: an adopter who writes `[gates.pre_merge]` with `native = "..."` today has cheap policy natives and a *stub* for the thing they most want gated — that their tests pass. A gate engine whose only shipped test verifier is a fixture is not a credible differentiation layer (§8, "over-invest here"). The resolution: ship a real pack as `rezidnt verify` subcommands, leave the golden-path demo board on its fast stub, and let real projects wire the real verifiers. Depth and honesty both served.

## Invariant posture (enumerated, not waved past)

- **I5 (MCP-first) — HONORED.** Verifiers run inside a governed gate reached over the MCP/socket surface; no new out-of-band verifier channel. The pack is configured in the project spec's `[gates.<name>]`, the existing seam.
- **I6 (deterministic + interrogable; never coerce) — LOAD-BEARING here.** No network; pinned toolchain (Decision 4). The three inconclusive traps map to real failure modes (Decision 4) and are NEVER coerced to pass/fail. `gate_explain`/`debrief` must name the failing check — which test, which lint (Decision 4). `cost_ms` is RECORDED, not asserted (wall-clock varies across machines).
- **I7 (one static binary, no telemetry) — the bundling lever, framed honestly.** Shipping the pack as `rezidnt verify <name>` subcommands puts the verifier WRAPPERS in-binary (Decision 3) — no external verifier files to install. But `cargo-test` still shells out to the host `cargo`; "in-binary" is about the verifier wrapper, not its toolchain dependency, and the record says so plainly (Decision 3). No telemetry added.
- No badge, no new subject, no new PDP path, no new reducer arm, no new linked daemon dependency.

## Decision

1. **v1 pack contents — a minimal but credible core, fast-follow named.** v1 CORE = `cargo-test` (runs the project test suite) + `clippy` (lint) + `fmt-check` (formatting). These are the credible floor for "this diff is safe to merge." FAST-FOLLOW (their own slices, this arc): `secret-scan` (diff for committed secrets) + `dependency-audit` (advisory DB). DEFERRED (named, not dropped): coverage thresholds, arbitrary user-defined exec verifiers beyond argv, non-Rust ecosystems — each a later DR if demand arrives.

2. **native vs exec — a stated RULE, not case-by-case.** THE RULE: a verifier is **exec** when its verdict comes from a subprocess-natural external tool (`cargo test`, `cargo clippy`, `cargo fmt --check` all shell out — exec kind), and **native** when its verdict is a deterministic, in-process, CAS-replayable computation over the pinned inputs (`secret-scan` scanning the diff blob = native — no external tool, replayable from the CAS ref like the existing policy natives). By this rule the v1 core (cargo-test/clippy/fmt-check) is exec; `secret-scan` is native; `dependency-audit` is exec (it consults an external advisory DB).

3. **How the daemon LOCATES a real verifier — `rezidnt verify <name>` subcommands, invoked as exec argv.** The pack ships as subcommands of the same static `rezidnt` binary, invoked by the exec runner as `argv = ["rezidnt","verify","cargo-test", …]`. This serves the literal-I7 single-binary goal (no external verifier files to install) AND reuses the proven exec path — `resolve_one` already accepts an exec verifier by argv (`VerifierKind::Exec(Vec<String>)`), so the verifier wrapper is just a `rezidnt` subcommand emitting the §8 JSON document on stdout. **Rejected alternatives, recorded:** (a) *PATH lookup of external tools* — makes the verdict depend on ambient PATH state, an I6 determinism/reproducibility hazard, and pushes install burden onto the adopter; (b) *a verifiers directory* — reintroduces the "external files to install" problem I7 exists to avoid. **The honesty note (owner asked for this plainly):** bundling the wrapper in-binary does NOT bundle its dependency — `rezidnt verify cargo-test` still shells out to the host `cargo` toolchain. "In-binary" is the WRAPPER only. A machine without `cargo` cannot run the cargo-test verifier; that condition maps to **inconclusive/could-not-run** (Decision 4), never a silent pass and never a hidden failure. The single-binary claim is about distribution of the verifier logic, not elimination of toolchain prerequisites, and the record does not let that ambiguity stand.

4. **Determinism + inconclusive rules (I6) — the three traps mapped to real modes.** No network during a verifier run; the toolchain is pinned (a `rust-toolchain.toml`-class pin, so "same inputs → same verdict" holds across machines). The mapping, never coerced:
   - **compile error / toolchain absent** (no `cargo` on host, or the crate does not build) → **inconclusive (could-not-run)** — the verifier could not reach a verdict; it is NOT a test failure.
   - **test failure / lint violation / unformatted file** (the tool ran and reported a real defect) → **fail**.
   - **timeout / flaky** (exceeds the wall-clock budget, or nondeterministic) → **inconclusive (timeout)** — never coerced to pass or fail.

   **Interrogability:** `gate_explain`/`debrief` MUST name the specific failing check — which test (`auth::login`), which lint — carried as §8 evidence (a CAS ref, per I2), not a bare boolean. **`cost_ms` is recorded, not asserted:** wall-clock varies by machine, so the exit criterion records the per-verifier cost; it does not assert a bound (this is stated so no test pins a flaky wall-clock number).

5. **The golden-path demo board KEEPS its fast `tests-pass` exec stub.** `bins/rezidentd/tests/golden_path.rs` is NOT changed to run real `cargo test` — a real suite run there would make the one-take demo slow and host-toolchain-fragile for zero contract gain (the counterargument's honored force). The real pack ships for REAL project specs; the demo board proves the contract with its fast stub. Any acceptance criterion for the real pack lives in NEW tests (a `verify`-subcommand harness), not by mutating the golden-path board.

## Consequences

- **Roadmap (§8 / §16).** §8 gains a named v1 production verifier pack (core: cargo-test/clippy/fmt-check as exec; fast-follow: secret-scan native, dependency-audit exec) shipped as `rezidnt verify <name>` subcommands. No new phase — this is S4 depth atop the proven engine. Suggested slicing (each done = criteria pass /vet + /debrief): `verify-subcommand` (the `rezidnt verify` dispatch + one real exec verifier, cargo-test, end-to-end through `resolve_one`) → `verify-lints` (clippy + fmt-check) → `secret-scan-native` → `dependency-audit`.
- **Risk register.** ADDS one honest risk in plain words: a real verifier's verdict depends on a HOST toolchain the static binary does not carry (`cargo`, `clippy`) — a missing toolchain must surface as inconclusive/could-not-run (Decision 4), never a silent pass; the mitigation is that the inconclusive trap is machine-enforced by the §8 runner, not left to convention. CLOSES a standing gap: §8's shipped test verifier was a fixture stub.
- **Test/criterion honesty (plain words).** This record WEAKENS no test and lowers no bar. It does NOT touch the golden-path board (Decision 5) — the fast stub there is retained deliberately, and that retention is stated so no one mistakes "the demo still uses a stub" for a regression. Acceptance for the real pack is NEW test surface, not a relaxation of any existing criterion. `cost_ms` is recorded, not asserted (Decision 4) — this is a deliberate non-assertion of a flaky value, stated plainly, not a dropped check. No intel memo is cited by this record (no competitor source informed it; the exec contract and subcommand dispatch are the project's own S4 work).
- **Deferred, named (not silently dropped).** (a) coverage-threshold verifiers; (b) arbitrary user-defined exec verifiers beyond argv; (c) non-Rust ecosystems; (d) making the golden-path board run the real suite. Each is its own DR if demand arrives.

Amendments to this record require DR-042.
