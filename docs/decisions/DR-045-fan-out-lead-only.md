# Decision Record DR-045 — `fan_out` is lead-only: an operator badge is refused at the door

**Date:** 2026-07-24
**Status:** ACCEPTED (owner, 2026-07-24)
**Amends:** [DR-044](DR-044-live-lead-sub-fanout.md) §Decision 1 ONLY — adds the door semantic that record left undefined (which badge *kinds* `fan_out` admits). DR-044 §Decision 1's args and verb derivation and §Decision 2's edge keying **stand unchanged**; §Decisions 3–6 are untouched. Mints NO invariant, NO event subject, NO badge kind, NO tool, NO tool arg, NO PDP path, NO reducer arm. Mints ONE additive refusal code. Owes NO `/subject`. Adds a §20 index row.

## Context

DR-044 §Decision 1 authorizes fan-out with "the lead's own badge [through] the existing §12 door with the existing verb `spawn`," and §Decision 2(b) requires the emitted `permit.delegated` to be keyed `run` = the LEAD's run. But the §12 door is **dual-path** (`crates/rezidnt-mcp/src/lib.rs:563-647`): path 1 admits the DR-005 opaque operator badge by token-equality against the `BadgeBook` (`:571-581`), path 2 verifies an agent macaroon and returns its sig-derived `badge_id` (`:640-646`). `call_spawn_agent` takes that door verbatim (`:680`). The operator badge is a **daemon-lifetime local-human badge** (DR-005 §Decision 3), a 32-byte opaque token (`crates/rezidnt-run/src/badge.rs:30-33`, `:56`, `:72`), not a macaroon (`:234`, `:316`) — and it **maps to no run**. So an operator-badge `fan_out` call passes the door with no lead run to key the edge on, and DR-044 never says what happens.

The mirror already exists. DR-032 made `kill_run` **operator-only** via a separate door, `check_operator_badge` (`crates/rezidnt-mcp/src/lib.rs:716-738`), which deliberately does not try the macaroon path — "terminating a run is an operator action, not an agent self-action." `kill_run` and `resolve_permit` use it (`:750`, `:827`). Taken together the two records give the surface a shape: **neither tool admits both badge kinds**, and each says which kind and why.

**Strongest counterargument (recorded, not just resolved).** This forecloses a plausible operator workflow. A human may reasonably want to fan out work directly and now must first spawn a lead agent it may not want — an ergonomic tax on a real use case, imposed to protect a graph property. The alternative considered was an explicit `lead_run` arg admitted only on operator calls. It is **deferred, not rejected on principle**: it widens the tool surface and adds a second authorization path with no demonstrated demand, and it can arrive additively later without breaking anything decided here.

The disposition rests on three things. It keeps **"every sub has a lead" total** — the orchestration graph can never contain an unparented sub. That is the same class of lie DR-044 was written to close from the other direction: its §Context documents a read side reporting a shape production never emitted, and an unparented sub would be production emitting a shape the read side cannot parent. The capability is **not withheld** — an operator already has `spawn_agent` for parallel runs; only the unparented delegation edge is refused. And it is the exact mirror of DR-032: killing is a human's prerogative, delegation is a run's.

## Invariant posture

**I5 — LOAD-BEARING.** The door is the governed surface's authorization statement; this record makes `fan_out`'s statement explicit rather than incidental. **I6 — LOAD-BEARING.** An operator badge is *valid*; it is the wrong *kind* for this tool. Refusing it as `badge.invalid` would tell the caller its badge is bad, which is false — an honesty regression. **I1, I2, I3, I4, I7, I8 — UNTOUCHED.**

## Decision

1. **`fan_out` is lead-only.** It admits ONLY an agent macaroon verified at the §12 door. A presented value that is an admitted DR-005 operator token is **REFUSED**, on policy, not on verification. Fan-out is a run-scoped capability. Structurally this is a third door beside `check_badge` and `check_operator_badge`, in the DR-032 shape.
2. **Refusal code: MINT `codes::FAN_OUT_LEAD_ONLY = "fan_out.lead_only"`.** New, not a reuse — dotted-lowercase per the existing `codes` vocabulary (`crates/rezidnt-mcp/src/lib.rs:49-81`), sibling to DR-044's `fan_out.too_wide`. Additive: older peers already tolerate an unknown refusal code (the DR-035 `scope.requires_ttl` precedent, `:75-80`).
3. **Refusal precedes any effect.** Door order: no `badge` arg → `BADGE_REQUIRED`; an admitted operator token → `FAN_OUT_LEAD_ONLY`; an unparseable or unverifiable macaroon → `BADGE_INVALID`; only then the DR-044 §Decision 4 width cap, then the substrate. A refused call allocates no worktree, spawns nothing, and writes no fact — the same house pattern as the width cap.
4. **The refusal is distinguishable from a failed badge.** `FAN_OUT_LEAD_ONLY` ≠ `BADGE_INVALID`, and its message says the tool is lead-only rather than that the badge failed. Stated plainly for triage: because the refusal precedes any effect, **no fact reaches the log, so `gate_explain` has nothing to show** — it resolves only recorded gate/permit verdicts for a run (`:1491-1517`). The tool result's code IS the interrogable surface here, which is why it must be its own code. This record does NOT retrofit DR-032's door, which still returns `BADGE_INVALID` for a macaroon (`:733-736`); that conflation is noted, not fixed here.

## Consequences

- **Roadmap.** No new slice. This folds into the in-flight DR-044 build slice as a door condition. §19's register line is unchanged.
- **Risk register.** REMOVES: an unparented sub in the orchestration graph is now structurally unreachable. ADDS: the operator-ergonomics gap in §Context — an operator wanting parallel work must spawn a lead or use `spawn_agent`.
- **Test/criterion honesty, plain words.** This record **weakens no test and lowers no bar**, and relaxes no verifier semantics. It owes one machine-checked guard: **a `fan_out` call carrying a valid operator badge is refused with `FAN_OUT_LEAD_ONLY` and emits NO `worktree.allocated` and NO `agent.spawned`**, plus a non-vacuity leg proving a real lead macaroon on the same core IS admitted. **Correction to the premise this record was drafted against:** the oracle's unit board `crates/rezidnt-mcp/tests/fan_out_door_and_width_cap.rs` does **not** present a lead macaroon — it mints an operator badge and presents `operator.token_hex()` on every admitted path (`:261-277`, `:295-310`, `:384-397`, `:454-467`), and `core_with` (`:211-222`) wires no root key, so that core cannot verify a macaroon at all (`crates/rezidnt-mcp/src/lib.rs:586-591`). Four of its five tests therefore assert the behaviour this record forbids and must be re-cut onto a real macaroon over a root-keyed core (`McpCore::with_root_key`, `:409`); only `the_badge_door_runs_before_the_width_cap` (`:336`) survives untouched. The daemon board `bins/rezidentd/tests/fan_out_live_e2e.rs` DOES use the injected `REZIDNT_BADGE` macaroon (`:25-32`, `:237-247`) and is unaffected. The operator-badge path is genuinely uncovered today.
- **Deferred, named.** An explicit `lead_run` arg admitting operator-initiated fan-out under a second authorization path. Deferred for want of demonstrated demand, additive when wanted, and reachable by a future record without amending this one.

Amendments to this record require DR-046.
