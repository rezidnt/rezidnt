# Decision Record DR-043 — Unblock the `secret-scan` native verifier: pin the diff's added content to CAS as a new input ref

**Date:** 2026-07-24
**Status:** ACCEPTED
**Amends:** [DR-041](DR-041-production-verifier-pack-v1.md) Decision 2 (native vs exec rule) — KEEPS `secret-scan` classified NATIVE, and closes the input-shape gap that made that classification unbuildable. Amends the §8 verifier INPUT CONTRACT for `pre_merge` natives: adds a per-file added-content CAS ref alongside the existing path-status summary. Mints NO new invariant, badge, PDP path, reducer arm, or daemon dependency. Whether a NEW event subject/field is owed is flagged for the warden (Decision 4), not minted here. Adds a §20 index row.

## Context

DR-041 Decision 2 stated the rule: `secret-scan` is **native** because its verdict is "a deterministic, in-process, CAS-replayable computation over the pinned inputs … scanning the diff blob." The Lane A implementer, building the `secret-scan-native` fast-follow slice, found the rule unbuildable as written. At the `pre_merge` gate the daemon passes natives a **content-free path-status summary** only: `<letter>\t<path>` lines built by `git_diff_summary` (`bins/rezidentd/src/gates.rs`), pinned into `refs["diff"]` at `bins/rezidentd/src/runs.rs:1576`. The git adapter never `cas.put()`s per-file content, and natives explicitly ignore cwd (comment at `runs.rs:1589` — exec verifiers alone see the live worktree via `exec_cwd`). So a native `secret-scan` has **no file bytes to scan**: it cannot detect a hardcoded key inside a changed file. Shipping it against the current input shape would be an I6-dishonest label — a verifier named "secret-scan" that structurally cannot see secrets.

**Strongest counterargument (recorded, not just the outcome).** This is a daemon-side §8 input-shape change touching `gates.rs`/`runs.rs` for the sake of ONE verifier — is the cheaper fix not to reclassify `secret-scan` as **exec** and let it read the live worktree via `exec_cwd`, like `cargo-test`? That is real force: exec-with-cwd needs zero change to the native input contract and reuses a path that already works. It fails anyway on the invariant that made "native" correct in the first place. An exec verifier reading the **live worktree** makes its verdict depend on **unpinned, mutable on-disk state** — the tree can differ from the diff that the gate actually verified, and the verdict is not reconstructable from the log alone. That is an I3/I6 determinism regression: `secret-scan` would no longer be replayable from content-hashed inputs. Option A keeps the verdict a pure function of a **CAS-pinned content ref** — replay-equivalent by construction — which is exactly the property that earned `secret-scan` the native label. The cost is a bounded, honest input-contract amendment; the exec shortcut trades away the invariant.

## Invariant posture (enumerated, not waved past)

- **I2 (control/data never mix; ≤32 KiB → CAS) — the canonical case, load-bearing.** The added content is BYTES; it is `cas.put()`-ed and carried as a **CasRef**, never inlined on the fabric. This is precisely the bytes→CAS rule I2 exists for — diff content is out-of-band by design. No payload crosses the control plane inline.
- **I3 (log is truth; state derived) — the reason Option A wins.** The verdict is replayable from the pinned content ref (content-hashed input → same verdict), not from mutable worktree state. This is what the exec-with-cwd alternative would have forfeited.
- **I5 (MCP-first) — HONORED.** `secret-scan` stays a governed `pre_merge` gate input over the existing surface; no new out-of-band verifier channel. A new *input ref* rides the existing gate-refs map, not a new channel.
- **I6 (deterministic + interrogable; never coerce) — the honesty fix.** With real content pinned, `secret-scan` can honestly reach `pass|fail|inconclusive` over the changed bytes. A scanner that cannot see content is the dishonest state we are leaving; inconclusive (e.g. binary/oversized blob it will not scan) is never coerced to pass.
- **I7 (one static binary, no telemetry) — UNTOUCHED.** No new dependency: the content ride reuses the EXISTING CAS. No new artifact, no phone-home.

## Decision

1. **Keep `secret-scan` NATIVE (DR-041 Decision 2 stands).** The native/exec rule is reaffirmed, not overturned; this record makes the native classification buildable rather than reclassifying to exec.
2. **The daemon's git adapter `cas.put()`s the per-file ADDED CONTENT of the diff** and exposes it as a NEW pinned input ref alongside the existing path-status summary — e.g. `refs["content"]` as a content `CasRef`, sitting next to the current `refs["diff"]` summary built at `runs.rs:1576`. The existing `git_diff_summary` path-status output is unchanged and retained.
3. **The native `secret-scan` scans that pinned content ref**, not the live worktree and not the path-only summary. Its verdict is a pure function of the content-hashed ref — CAS-replayable, matching the property DR-041 Decision 2 asserted.
4. **Oversized / non-text content is handled by the three-valued I6 rule, not coerced.** Content the scanner cannot faithfully read (binary blobs, or a blob exceeding a scan bound) folds back as **inconclusive**, never a silent pass. The added-content ref is subject to the same I2 ≤32 KiB → CAS discipline as any payload.

## Consequences

- **Roadmap (§8).** Unblocks the `secret-scan-native` slice, the remaining v1-pack fast-follow. Recorded status of the arc: `verify-lints` (clippy + fmt-check) and `dependency-audit` **already shipped this session**; `verify-subcommand` and the core exec pack landed earlier; `secret-scan-native` is the last open v1-pack slice, and this DR is its precondition. No new phase, no new crate.
- **Risk register.** ADDS one honest risk in plain words: emitting per-file added content to CAS widens what the daemon pins per diff — the mitigation is the existing I2 ≤32 KiB → CAS discipline (large content becomes a ref, is not inlined) and the inconclusive trap for content the scanner will not read. CLOSES the standing gap that DR-041 Decision 2's native label was structurally unbuildable at `pre_merge`.
- **Test/criterion honesty (plain words).** This record WEAKENS no test and lowers no bar; it makes an honest verdict possible where none was. It does the opposite of relaxing `secret-scan` — a scanner that could not see content was the dishonest state. What the build slice OWES, named so a green `/vet` today is not mistaken for coverage: (a) **an input-contract pin** — the new content ref is an amendment to the §8 native input shape; pin it with a test that the ref is present and content-correct at `pre_merge`; (b) **a CAS-replay-equivalence test** — the `secret-scan` verdict recomputes identically from the pinned content ref alone (the I3 property this whole record turns on); (c) **the inconclusive-on-unscannable-content path** exercised, proving it is never coerced to pass. No intel memo is cited by this record.
- **Deferred, named (not silently dropped).** Whether the content ref requires a **new event subject/field** is a warden question, not settled here: if the ref rides EXISTING fold facts (the diff/CAS facts already emitted at `diff.ready`), NO new subject is owed; if it does not, that is a `/subject` (warden) call — the build slice must FLAG it and MUST NOT mint a subject on its own. Also deferred: extending the content ref to natives other than `secret-scan` (none need it today) — a later question if a second content-reading native appears.

Amendments to this record require DR-044.
