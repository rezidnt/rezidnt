## Context

**1. Sample identity — today's dedup is fatal to N samples of one task.** `FanOutTask.idempotency_key` is REQUIRED and resolves through the per-workspace `spawn_keys` map, log-derived from `agent.spawned.idempotency_key` (`crates/rezidnt-types/src/mcp.rs`'s `FanOutTask` doc comment; the map itself in `bins/rezidentd/src/mcp.rs`). Same key ⇒ same run, nothing spawned — correct for a retried fan-out task, fatal for N samples of one task, which are supposed to be N distinct runs.

**2. `fan_out` cannot be reused, on two independent grounds.** (i) `fan_out` is lead-only by ratified design (DR-045 §Decision 1): only a verified agent macaroon is admitted, and the emitted `agent.spawned.lead_run?` requires a real lead run to key on. A trial has no lead — reusing `fan_out` means either fabricating one or widening a door DR-045 deliberately closed. (ii) Decision 1 below requires the daemon to know the whole matrix up front to derive keys, which forecloses caller-side task expansion — the shape `fan_out` assumes.

**3. What is minted, run through the DR-006 discipline** (no consumer-less subjects; prefer a field when an existing fact can carry it; refuse synonyms).
- `trial.opened` earns a subject, not a field: it is a genuinely new event in time, preceding N spawn facts and 1:1 with none of them. Necessity: `FanOutTask`'s ratified refusal shape means a worktree-conflicted task mints no run and is reported REFUSED on the *tool response*, never the log (`crates/rezidnt-types/src/mcp.rs`'s `FanOutTask` comment: "reported REFUSED, never as a passed, failed, or inconclusive sub"). Without a durable record of intent, a 3×3 matrix that spawns 7 is indistinguishable on the log from 7 unrelated runs, and the two missing samples are invisible to any fold.
- `agent.spawned.trial?` earns a field, not a join: it is fixed at spawn, 1:1 with the spawn fact — the same discriminator that gave `lead_run?` and `role?` field status. Correlation cannot carry it: DR-049 established that join is unsound for this shape, since one correlation is minted per spec and threaded into every sibling, spanning N runs and N worktrees.
- `agent.spawned.model?` earns a field: `AgentSpec.model` (DR-048 slice A) reaches spawn argv via `push_model_flag` (`crates/rezidnt-run/src/spawner.rs`) and the spec preimage (`crates/rezidnt-run/src/spec.rs`) but is **never written to `agent.spawned`** — confirmed absent from the ratified v1 payload block in `spec/ontology.md`. A leaderboard folded from the log cannot attribute a result to a model without reaching through the spec's CAS preimage, which exists only if a gate pinned it — load-bearing for a feature whose point is comparing models.
- `variant?` is REFUSED as a synonym: a variant is (agent, harness, model), and `agent.spawned` already carries `agent` and `harness` in the S1 baseline; with `model?` minted, all three axes ride facts already present. A fourth field naming the same triple is exactly what DR-006 refuses.
- `trial.scored` is REFUSED, prominently, retiring a queued item rather than re-minting it by habit: DR-048 §Context already rules the leaderboard "just another fold — I3 makes history free," and the DR-022 collator is a pure fold over the recorded log. Scoring is derived state, not a fact; putting a computed projection on the log is precisely what I3 forbids.

**4. Backpressure — no new mechanism.** A trial's V variants × N samples multiplies worktree allocations exactly as fan-out width does, and DR-048 v1 already states the cap is the *only* backpressure — `rezidnt-supervise` does not exist in this tree. Naming a scheduler here would be inventing infrastructure this arc has repeatedly declined to build ahead of demonstrated need.

**5. Scoring is out of slice B.** "Scored via existing gate events" (DR-048 §Decision 4) means slice B makes the runs spawnable and attributable; collation and the leaderboard are slice C.

**6. The consumer obligation this inherits.** The DR-050 set's consumer (3) requires the slice-C collator to treat a `contract_violated` run's accounting as UNTRUSTED (`spec/ontology.md`: "the fact exists precisely so turn-1 totals published as RUN totals cannot silently win a trial" — confirmed NOT BUILT, ratified slice-C scope). DR-054 (ACCEPTED, `cf44f01`) makes `rezidnt debrief` exit 3 for such a run and explicitly defers widening `RunRow`/`SubRow` to slice-C scoping. A trial's samples can and will include premise-broken runs; a collator built on `SubRow` as it stands cannot comply with the DR-050 set's own consumer (3) without that widening. Slice B does not build the collator — it names the obligation so slice C does not silently forget it.

**7. Emitter reachability — stated plainly, not soft-pedalled.** `SUPPORTED_HARNESSES = &["claude-code"]` (`bins/rezidentd/src/runs.rs`) — the daemon admits no other harness on any live path. A slice-B trial today can vary agent-spec and model *within* claude-code; it cannot vary harness. Since the matrix's headline axis is harness × model comparison, that comparison is **prospective**, not live, until `SUPPORTED_HARNESSES` widens — a fact this record states rather than implies.

## Decision

1. **Sample identity is daemon-derived, deterministically, from the trial's own key.** `open_trial` takes ONE trial-level idempotency key (mirroring `SpawnAgentArgs`'s single required key, not `FanOutTask`'s per-task key) and the daemon derives each sample's spawn key as a deterministic function of that key plus its (variant, sample-index) pair. Re-running the same trial re-derives identical N keys, so retry dedupes exactly as before; N samples of one trial get N distinct identities. **This WEAKENS NOTHING**: the dedup rule (same key ⇒ same run, scope per workspace) is untouched and resolves through the EXISTING `spawn_keys` map — only the key *space* is extended, by the caller of the map rather than by the map. *Rejected: (a) caller-supplied per-sample keys — weakens nothing either, but pushes retry bookkeeping onto the caller and is incompatible with Decision 2's server-side expansion; (b) a dedup-scope discriminator for sample identity — this WOULD change the rule and is the weakening DR-048 warns against.* The exact derivation function (hash choice, input framing) is left to the implementer, flagged not silent: it MUST be deterministic, collision-resistant across trials, and log-derivable from `agent.spawned.idempotency_key` alone — the properties `agent.spawned.badge_id`'s `hex(blake3(sig)[..8])` derivation already demonstrates as a house pattern (DR-018 §Decision (a)), though this record does not pin that specific function.

2. **One new mutating MCP tool, `open_trial`, operator-badged only.** Mints `OpenTrialArgs`/one schemars type, §9 no-drift. A trial is opened by an OPERATOR, not a lead agent — the mirror of DR-045 in the other direction: DR-045 admits only a macaroon on `fan_out` because the edge needs a real lead run to key on; `open_trial` has no lead and no edge to key, the same condition `kill_run`/`resolve_permit` are in, so it reuses `check_operator_badge` VERBATIM (`crates/rezidnt-mcp/src/lib.rs`) — no verb parameter, **no new refusal code**. A presented agent macaroon simply fails the operator-token check and falls through to the existing `BADGE_INVALID`, the same conflation DR-045 §Decision 4 declined to fix on `kill_run`'s door and does not fix here either. Server-side matrix expansion is required by Decision 1: the daemon must see the whole matrix (variants × samples) before it can derive keys, foreclosing caller-side expansion.

3. **Mints, per §Context 3:** subject `trial.opened`; fields `agent.spawned.trial?`, `agent.spawned.model?`. Refused: `variant?` (synonym once `model?` lands), `trial.scored` (derived state, not a fact — retired, not re-queued).

4. **Backpressure inherits `fan_out`'s model exactly; no scheduler is built.** The whole call is refused, before any effect, when V×N exceeds a DEFAULT cap — the `FAN_OUT_TOO_WIDE` precedent, refused whole, never partially spawned. No queue, no new mechanism. **Named as risk, not fixed:** V×N real agent runs is genuinely heavy; whether slice C or D needs a queue is a measurement question, not decided here. DR-048 risk (2) — N-sample spawning multiplies the per-allocation watcher/registry leak — is **mitigated, not eliminated**, by DR-049's release lifecycle, which has since landed (16/16, merged): a trial's failed samples still accumulate exactly as any failed run does today (no TTL), so heavy trial use still grows the failed-tree backlog DR-049 named and accepted.

5. **Scoring is OUT of slice B.** Slice B delivers spawnable, attributable samples only. Collation, tokens, wall-time comparison, and the leaderboard are slice C (DR-048 §Decision 4); winner-take-all selection is slice D. Cross-vendor token comparison stays refused per DR-048 §Decision 3.

6. **Ledger (DR-053 §Decision 5 form):** invariant NONE · subject `trial.opened` · field `agent.spawned.trial?`, `agent.spawned.model?` · trait method ONE (`McpSubstrate::open_trial` — the daemon seam the tool dispatches through; NOT one of the four §7-bound traits, so not an I4 matter, precedent DR-011 §Decision 1 as ratified by DR-052 item (a)) · dep NONE. **Plus ONE refusal code, `TRIAL_TOO_WIDE` (§Decision 7).**

7. **The over-wide refusal carries its OWN code, `TRIAL_TOO_WIDE` — a same-day ledger correction, not a design change.** §Decision 4 rules that an over-wide matrix is refused whole; it invoked the `FAN_OUT_TOO_WIDE` *precedent* for the SHAPE of that refusal (whole-call, before any effect, never partially spawned) and the Amends banner then wrongly read that as reusing the *code*. Reusing `FAN_OUT_TOO_WIDE` on `open_trial` would answer an operator with a refusal naming a tool they never invoked — the exact I6 interrogability defect corrected in `loopback_post` on 2026-07-26, where a generic helper's error contexts named `kill_run` for every proxied call. So a distinct code is required by §Decision 4's own design, and the banner is corrected rather than the decision. **Note the asymmetry with §Decision 2 deliberately:** the DOOR mints no code (a presented macaroon falls through to the existing `BADGE_INVALID`, exactly as on `kill_run`), because there the existing code is *accurate*; the CAP mints one, because there the existing code would be *false*. Reuse is right when the borrowed code still tells the truth, and wrong when it does not. *(Considered and rejected: minting DR-056 for this. DR-052 ratified five such items against DR-049 as disclosure corrections — a banner missing a mint the decision already authorized in substance. Nothing had been built against the old ledger; the oracle pass caught it before implementation, which is the point of oracle-first.)*

8. **A matrix carrying DUPLICATE variant triples is REFUSED at the door** (`ARGS_INVALID`, no new code), following `FanOutArgs`'s ratified treatment of an empty task list: a zero-task call "is a caller bug and is answered loudly, never with an empty outcome vector that a broken caller could read as a fan-out that happened." Two identical (`agent`, `harness`, `model`) triples are indistinguishable in every downstream artifact — the delta projection groups by variant, and a leaderboard would carry two rows that are the same variant — so admitting them injects ambiguity into precisely the output this arc exists to produce. A caller wanting more samples of one variant raises `samples`, which says so unambiguously. *(Considered and rejected: admitting them, since the derivation keys on variant INDEX and would not collide. It would work mechanically and read as a silent narrowing of meaning, which is the failure class this arc has fought throughout.)*
