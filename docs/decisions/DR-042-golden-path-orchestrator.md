# Decision Record DR-042 — Golden-path multi-agent orchestrator (lead → parallel sub-runs) over the worktree registry

**Date:** 2026-07-24
**Status:** ACCEPTED
**Amends:** §19 (adds a ratified-but-phase-gated "first-party orchestrator" line to the open-decisions register, and records its sequencing posture — Phase-3-gated, riding existing rails). Reaffirms — does not touch — I1, I2, I3, I4, I5, I6, I7, I8. Mints NO new invariant, subject, ontology fact, badge, PDP path, reducer arm, or daemon dependency. A lead↔sub lifecycle subject, IF one is owed, is deferred to a `/subject` (warden) session, not invented here. Adds a §20 index row.

## Context

Intel memo [`intel/002-omnigent-capability-comparison.md`](../../intel/002-omnigent-capability-comparison.md) (F2, and the synthesis "Exposed" list) names this as rezidnt's sharpest exposure: Omnigent ships a working lead-agent → parallel-worktree sub-agent orchestrator (the "Polly" pattern) as a marquee capability — a lead run plans and delegates to coding sub-runs in **parallel isolated git worktrees**, then folds their work back. rezidnt has the *rails* — the §7 worktree registry (canonicalized path + `allocator` field, `worktree.conflict` on double-claim), the `AgentSubstrate` trait, the supervisor — but **no golden path** that spawns a lead run which fans out to N sub-runs in isolated worktrees and folds their dossiers back. If "fleet of agents" is the pitch, this is a visible competitor capability rezidnt does not yet demonstrate end-to-end.

The memo also hands us the wedge (takeaway F1/#1): Omnigent holds session state **imperatively in a server-of-record**; rezidnt's structural edge is that fleet state is derived from a replayable append-only log. So the orchestrator is not a "match Omnigent" copy — it is the same capability built the rezidnt way: the orchestration graph (which lead spawned which subs, their status, their folded results) is a **pure fold over events (I3)**, replayable as evidence, never held in a mutable in-daemon session object. That is the differentiator the exposure lets us convert.

Per DR-002 rule 3, this memo is influence/positioning input only — F2 traces *what capability* and *what gap*, not code. No Omnigent code was read; nothing is ported (I8). The memo's own coverage-gaps note (§Coverage gaps) already flagged that matching F2 "would imply new orchestration subjects, flagged for a future DR only" — this is that DR, and it honors the flag by deferring the subject to a warden pass.

**Strongest counterargument (recorded, not just the outcome).** This is Phase-3 scope gravity in its purest form. The sequencing law is fabric → gates → terminal/orchestration-last, and a multi-agent orchestrator is precisely the interactive-fidelity pull the plan warns against; the honest worry is that "fleet orchestration" outruns the depth of what rides beneath it. The force of this is real and is honored the DR-038 way — by stating plainly whether the substrate exists, not by refusing the work. The load-bearing fact: the fabric, the gate engine, the run substrate, and the worktree registry this orchestrator rides on **already exist and are proven green** — the S3 MCP surface demo is end-to-end (session-22 handoff), the S4 golden path is built, and the DR-041 verifier pack is accepted. An orchestrator here is *composition of shipped rails*, not new-substrate-before-fabric. What it is NOT clear of is roadmap sequencing: it is a Phase-3 capability by the plan's own law. The resolution (Decision 5) is therefore to **ratify the shape and the invariant contract now, but gate the live golden-path wiring to Phase 3** — design/prototype free, single-writer fan-out/fold wiring gated — exactly as DR-038 gated only its live-daemon wiring.

## Invariant posture (enumerated, not waved past)

- **I1 (zero pixels in core) — PRESERVED.** The orchestrator is headless: a governed capability of `rezidentd`, no render. Any UI (board panel, `rezidnt-operator` graph view) is a downstream MCP client reading the derived orchestration graph — buttons follow tools.
- **I2 (control/data never mix) — HONORED, load-bearing here.** The lead↔sub channel carries facts and refs only: sub-run *payloads* (dossiers, diffs, transcripts) are ≤32 KiB or become CAS refs; a sub-run folds back a `CasRef` to its diff/dossier, never inline bytes on the fabric. This is called out because "fold results back" is exactly where an orchestrator is tempted to shove diffs through the control plane — it must not.
- **I3 (log is truth; state derived) — THE MECHANISM.** The orchestration graph (lead→sub edges, sub status, fan-out width, folded verdicts) is a **pure fold over existing/owed facts**, droppable and rebuildable via `rezidnt rebuild`. No mutable in-daemon "orchestration session" object of record (the explicit inverse of Omnigent's server-held state, memo F1). This is the wedge; violating it forfeits the whole reason to build our own.
- **I4 (substrates behind traits) — REUSE, no new backend.** Sub-runs spawn through the existing `AgentSubstrate::spawn` under the supervisor (§7 backoff/breaker/health facts); isolation is the existing **worktree registry** — each sub-run gets a registered worktree (canonicalized path, `allocator` field = the orchestrator/lead, `worktree.conflict` on double-claim). NO new isolation substrate, NO new run backend is minted. The registry's two-allocators design already anticipates a delegating allocator.
- **I5 (MCP-first) — HONORED.** Orchestration is exposed as a **governed MCP tool/capability first**, UI-second (fan-out/status/fold are surfaced through the §9 MCP surface with schemars-generated, oracle-pinned args — §9 no-drift). rezidnt already exposes its fleet as an MCP server (memo F4 edge); this extends that surface. The lead run is itself a first-class MCP operator of its sub-runs.
- **I6 (verifiers unchanged) — UNTOUCHED.** Sub-run results are gated by the *existing* verifier engine and DR-041 pack; `pass|fail|inconclusive` stays three-valued, inconclusive never coerced. The orchestrator folds verdicts; it does not create a new verdict path or relax one. A sub-run that comes back inconclusive folds back as inconclusive.
- **I7 (one static binary, no telemetry) — UNTOUCHED.** No new artifact, no new dep, no phone-home. Orchestration is composition inside the existing daemon binary.
- **I8 (clean-room) — APPLIES.** Nothing is ported from Omnigent; the memo is influence-tracing (capability + gap), not code. Boring deps only, and none new.

## Decision

1. **Ratify a first-party, headless golden-path orchestrator**: a **lead run** that can fan out to N **sub-runs**, each spawned via the existing `AgentSubstrate` under the supervisor, each isolated in its own registered worktree from the existing §7 registry. NO new isolation substrate or run backend (I4).
2. **The orchestration graph is a pure fold over events (I3)** — lead↔sub lifecycle, fan-out width, sub status, and folded results are derived and `rebuild`-able, never held as a mutable in-daemon session of record. This is the non-negotiable design constraint, not an implementation detail.
3. **Result-fold is control-plane-clean (I2):** sub-runs fold back facts and `CasRef`s (dossier/diff by reference, payloads ≤32 KiB → CAS). No inline bytes cross the fabric.
4. **Exposed MCP-first (I5):** the fan-out / status / fold capability is a governed MCP tool with schemars-generated, oracle-pinned args (§9 no-drift) before any keybinding or GUI panel. Verdicts are folded through the *existing* verifier engine (I6, DR-041) — no new gate path.
5. **This record GATES the live golden-path wiring to Phase 3; it does not authorize it now.** Design, the fold/graph reducer prototype, and the MCP-surface sketch are FREE to proceed. Wiring a lead run to *live* fan-out on the golden path is a Phase-3 slice, sequenced behind the fabric→gates→orchestration law — this record ratifies the shape and the invariant contract so the eventual slice inherits a settled posture, exactly as DR-038 gated only its live wiring.
6. **Any new lead↔sub lifecycle fact is owed to a `/subject` (warden) session**, not invented here (memo's own coverage-gaps flag). The first-fold design should first attempt to derive the graph from *existing* facts (agent spawn/signal/health, worktree allocation/conflict, dossier folds); a new subject is minted only if the graph genuinely cannot be folded from what exists — and only by the warden.

## Consequences

- **Roadmap (§19).** ADDS a ratified-but-Phase-3-gated "first-party golden-path orchestrator (lead → parallel sub-runs over the worktree registry)" line to the open-decisions register, closing the memo-F2 exposure as *decided in shape*, and records its sequencing posture: it rides shipped rails (fabric/gates/run substrate/worktree registry all green), but its live golden-path wiring is a Phase-3 slice by the sequencing law. No new phase, no new crate, no golden-path change lands from this record itself.
- **Risk register.** RESOLVES (in shape) memo-002 risk-signal (2): "Omnigent's shipped sub-agent orchestration is a category-narrative competitor if rezidnt's 'fleet' pitch outruns its demonstrated multi-agent path" — rezidnt now has a decided, invariant-clean answer, differentiated by log-is-truth (the graph is replayable evidence, not server-held session state). ADDS one honest risk in plain words: an orchestrator is the archetypal place I3 rots — the temptation to hold a live orchestration session imperatively for convenience is strong; Decision 2 is the guard, and the eventual slice owes a `rebuild`-equivalence test proving the graph folds from the log alone. A second honest risk: fan-out multiplies worktree allocation and supervisor load — the registry's `worktree.conflict` fact and the §7 crash-loop breaker are the existing mitigations, but fan-out width should be bounded (a cap, sized in the Phase-3 slice, not here).
- **Test/criterion honesty (plain words).** This record WEAKENS no test and lowers no bar. It relaxes no verifier semantics — sub-run verdicts fold through the unchanged I6/DR-041 path, and an inconclusive sub-run folds back inconclusive, never coerced to pass. It adds no machine-checked guard of its own (it is a scope/shape decision); the eventual Phase-3 slice owes: (a) the §9 no-drift schema pin for the new MCP tool, and (b) an I3 fold-equivalence test (graph rebuildable from log alone). Those obligations are named here so a green `/vet` today is not mistaken for orchestrator coverage.
- **Deferred, named (not silently dropped).** (a) The lead↔sub lifecycle **subject** — owed to a `/subject` (warden) session, and only if the graph cannot fold from existing facts (Decision 6). (b) The **live golden-path fan-out slice** — Phase-3-sequenced, its own future DR/slice with the two owed tests above. (c) **Fan-out width bound / backpressure policy** — a Phase-3 slice detail, not decided here. (d) **Sub-run harness heterogeneity** (Omnigent mixes harnesses per orchestration, memo F2) — explicitly OUT of this record; single-substrate fan-out first, mixed-harness a later question.

Amendments to this record require DR-043.
